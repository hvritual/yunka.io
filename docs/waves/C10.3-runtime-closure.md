## Goal

Close the C10 generated assembly through the existing Yunka runtime spine without introducing a second runtime owner:

```text
AssemblyPlan
   ↓
generated typed Bootstrap
   ↓
framework/kernel
   ↓
core.App                      ← only lifecycle owner
   ↓
Platform Provider
   ↓
typed Modules
   ↓
Applications + C9 Executor
   ↓
explicit REST / gRPC / internal Operations
   ↓
Health + Diagnostics + Application Graph
   ↓
yunka dev readiness / closure
```

C10.3 does not own new authorization, transaction, idempotency, identity, request scope, business dispatch, listener discovery, shell command discovery, deployment topology, or restart policy.

## A — App-owned runtime components

`core.RuntimeComponent` is a lifecycle-only leaf:

- explicit name;
- optional Start callback;
- optional Health callback;
- optional Shutdown callback.

It intentionally has no service payload, lookup API, registry, or runtime field injection.

`core.App` remains the owner of lifecycle ordering:

1. Platform/ContextFactory starts;
2. typed modules start in catalog order;
3. runtime components start in deterministic name order;
4. health includes Platform/modules/runtime components;
5. shutdown reverses runtime components first, then modules, then Platform capabilities.

`core.RuntimeInventory` is secret-free read-only evidence. It contains explicit route/RPC/event-bus presence and does not expose addresses, credentials, caller scopes, payloads, or product configuration.

## B — Kernel bootstrap

`kernel.Bootstrap[T]` is sequencing, not a runtime object:

```text
kernel.New
  -> typed Build
  -> typed Register
  -> existing App.Start
```

Its result contains only the existing `*core.App` plus typed Applications. It has no Start/Shutdown methods.

Build/Register failure cleans the constructed App. `core.App.Start` remains responsible for lifecycle-start rollback.

## C — Generated runtime bootstrap

Only `CompileBoundAssembly` receives runtime bootstrap augmentation because that path has already proven explicit generated module Go bindings and `NewCatalog()`.

Generated `Bootstrap` reuses:

- generated explicit `NewCatalog()`;
- existing Platform Provider;
- generated `BuildApplications`;
- existing C9 `operation.Executor`;
- generated `RegisterTransports`;
- `kernel.Bootstrap`.

Static runtime inventory is derived only from canonical AssemblyPlan binding references joined back to canonical Manifest paths. Internal-only Operations remain transport-free.

## D — Explicit HTTP/gRPC lifecycle adapters

`framework/runtimecomponent` adapts caller-owned standard servers into App-owned lifecycle leaves.

HTTP requires explicit:

- `*http.Server`;
- `net.Listener`.

Shutdown uses bounded `http.Server.Shutdown(ctx)`.

gRPC requires explicit:

- `*grpc.Server`;
- `net.Listener`.

Shutdown uses `GracefulStop` and falls back to `Stop` when the supplied shutdown context expires.

Neither adapter infers listener addresses, TLS, secrets, environment, deployment topology, shell commands, or restart policy.

## E — Diagnostics and Application Graph closure

Existing `core.App.Diagnostics` remains the runtime inventory source.

Application Graph projects:

- runtime components as observed nodes;
- explicitly bound routes as observed runtime-route nodes;
- modules as observed runtime modules;
- process ownership from dev manifest as declared evidence;
- live process/diagnostic snapshots as observed evidence.

No graph edge is inferred from package names, process names, URL shape, or method naming.

## F — `yunka dev` closure hardening

### Compatibility boundary

Historical W10 closure allows ordinary dependency processes to own non-Application graph nodes without a diagnostics endpoint. C10.3 must not turn every local dependency into a Yunka application.

Therefore strict diagnostics readiness applies only when a process explicitly owns an Application Graph node whose kind is `application`.

### Plan / Run fail-closed rule

In closure mode, an Application-owner process must explicitly declare:

```text
Readiness != nil
DiagnosticsReady = true
CaptureDiagnostics = true
```

The readiness URL remains developer-owned local-runtime configuration. Existing URL/security validation remains authoritative.

This means `yunka dev plan --closure` and `yunka dev run --closure` fail before execution when an assembled Application owner has no verifiable Yunka health barrier.

Non-Application dependency processes retain the existing explicit graph ownership rules.

### Status fail-closed rule

`yunka dev status --closure` does not trust a runtime state JSON in isolation.

It first rebuilds the current explicit plan from:

- `.yunka/dev.json` or explicit `--config`;
- Application Graph or the existing contract-graph fallback;
- explicit targets;
- `--closure`.

It then validates the loaded runtime report against that plan.

The report passes only when:

- plan is a closure plan with runtime configuration;
- report application identity matches the plan;
- runtime state is currently `running`;
- report process plan exactly matches the current deterministic process plan;
- process inventory is complete and duplicate-free;
- each process retains the exact declared graph ownership;
- configured readiness processes are `ready`;
- non-readiness dependency processes are running;
- Application owners have captured diagnostics;
- Application diagnostics are live and ready and contain state evidence.

A stopped, failed, stale, partially ready, ownership-drifted, or diagnostics-free report fails instead of being printed as a successful closure.

The runtime state path used by `status --closure` is the explicit `runtime.statePath`. A conflicting explicit `--state` is rejected.

### Non-inference boundary

F adds no:

- command generation;
- shell execution path;
- listener/port discovery;
- process-name-to-Application inference;
- package scanning;
- environment secret discovery;
- automatic restart behavior.

- Application-owner diagnostics barrier remains explicit;
