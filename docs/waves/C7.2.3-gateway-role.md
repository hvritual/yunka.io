# C7.2.3 — Gateway Role typed vertical slice

## Base

`agent/c7-2-platform-request-scope@34eaaf191ee9dd58589cd972b98ba2022e369824`

C7.2.3 is the first real consumer migration after the C7.1 static module catalog and C7.2 App-owned Platform Provider / Request Scope foundation.

## Goal

Move the Gateway Role vertical slice away from request-time service pooling and runtime mutation while preserving the generated Gateway RPC contract and the existing one-App ownership model.

The migrated path is:

```text
modulecatalog Descriptor declares named DB capability
        ↓
platform.Provider prepares the App-owned database once
        ↓
restricted modulecatalog.BuildContext.Databases().GORM(name)
        ↓
long-lived stateless Role handler
        ↓
requestscope.Factory.New(ctx)
        ↓
request-owned GORM transaction + Role repository
        ↓
Role operation
        ↓
Commit / Rollback / Close
```

For typed gRPC, the generated bridge keeps an application-owned service through `rpcbridge.Static`; the service method itself creates the sole Request Scope. This deliberately avoids adding a second provider-owned request lifetime.

## Legacy boundary being reduced

The pre-migration compatibility adapter `ModuleGatewayProvider` acquires a pooled `core.Service`, constructs `request.Runtime`, calls `SetRuntime`, then calls `PutService` after the RPC finishes. C7.2.3 does not delete that compatibility adapter globally because remaining legacy consumers are deferred to C7.3. Instead, the migrated Gateway Role / typed RPC proof path must not use it.

The migrated path may not introduce:

- `request.Runtime` dependency acquisition;
- `GetService` / `PutService` service locator or pool access;
- `SetRuntime` request mutation;
- reflection-driven DI;
- lifecycle-bearing `sync.Pool`;
- DSN, connection factory or Platform configuration lookup inside Role business code.

An architecture regression test freezes this boundary.

## Role request scope

`RoleIntercept` no longer owns a long-lived Role repository. It owns only application-level collaborators (`router.Tree` and a `requestscope.ScopeFactory`). Every authorization or RPC method executes repository work through a fresh Scope.

`NewRoleInterceptWithDatabase` accepts an App-owned GORM pool, runs schema migration at composition time, creates the GORM Unit-of-Work factory, and binds a fresh `db.Store` to the current request transaction.

`NewRoleInterceptFromBuildContext` is the module-composition seam: the module supplies the database capability name declared in its descriptor, and the restricted BuildContext resolves only that App-owned named database. Role code never receives DSNs or factory configuration.

The filesystem SQLite constructor remains compatibility-only and delegates into the scoped implementation. New composition must use the typed BuildContext/database constructors.

## Request identity and authorization

Role middleware continues to participate in the legacy HTTP middleware surface for this subwave, but trusted identity is read from the runtime as a `context.Context` via `identity.FromContext`. `VerifyRoleApiRight` now accepts an explicit `context.Context`, so authorization queries inherit cancellation and request identity/metadata without a separate runtime lookup API.

Full removal of the legacy middleware `request.Runtime` type belongs to C7.3 after the remaining ingress path is migrated.

## Transaction semantics

For each Role database operation:

- one Request Scope is created;
- one GORM Unit of Work begins from the App-owned pool;
- the Role repository is bound to that request transaction;
- success commits and closes;
- error or cancellation rolls back and closes;
- the App-owned database pool is never closed by a request.

The existing Store-level atomic operations may use nested GORM transactions/savepoints inside the request transaction; ownership of the outer transaction remains the Request Scope.

## Typed RPC proof

The authenticated TLS `bufconn` integration no longer constructs `ModuleGatewayProvider`. It registers an application-owned stateless Gateway service with `rpcbridge.Static`. The service method creates its Request Scope and proves that the authenticated service-token Principal and RPC runtime metadata are visible in that scope.

The proof asserts:

- authenticated Principal reaches the scope;
- transport/protocol/operation metadata reaches the scope;
- one Unit of Work begins;
- success commits exactly once;
- rollback is not invoked on success;
- close executes exactly once.

## C6 business-method freeze baseline

C6 deliberately hash-froze the three `RoleIntercept` RPC method bodies while the transport stack was being replaced. C7.2.3 is the planned consumer migration that intentionally changes those method bodies to introduce explicit Request Scope ownership. The protobuf/API ABI remains frozen by the RPC/Contract gates; after the new behavior is verified, `tools/rpc-consumer-abi.json` is advanced once to the new scoped method bodies and remains a strict freeze for later waves.

Advancing that baseline is not a bypass: it is permitted only in this migration commit and is accompanied by typed consumer, TLS authentication, transaction, cancellation, race and contract-zero-drift tests.

## Deferred to C7.3

C7.2.3 intentionally does not yet delete:

- `ModuleGatewayProvider` compatibility adapter;
- framework reflection module container;
- `pkg/di`;
- remaining HTTP middleware `request.Runtime` interfaces;
- global compatibility App/config/store paths;
- other service/repository lifecycle pools.

C7.3 may delete these only after the remaining real consumers have moved to typed construction and explicit request ownership.

## Rollback

Revert the single C7.2.3 commit. RPC protobuf/generated contracts and persisted external schemas are unchanged.
