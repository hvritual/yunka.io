## Goal

Qualify the complete C11.4 fast-feedback loop with a real VCS-stamped Yunka CLI binary and a disposable typed consumer. C11.4-D adds qualification evidence only; it does not introduce any new fast-path decision or cache semantic.

The qualification flow is:

```text
clean framework checkout
        ↓
go build -buildvcs=true ./app/cmd
        ↓
real Yunka binary with verified engine identity
        ↓
disposable typed Application + Module consumer
        ↓
first generate = canonical full generation
        ↓
second generate = fast-generate
        ↓
check = fast-check
        ↓
--full generate/check = canonical paths
        ↓
corrupt generated output
        ↓
check = canonical drift failure
        ↓
generate = canonical recovery + evidence refresh
        ↓
generate/check = fast paths again
```

## Permanent gate

The same qualification test is automatically enabled in CI because GitHub Actions provides `CI=true`:

```text
TestC114QualificationRealBinaryFastFeedback
```

Local reproduction uses the exact same test:

```bash
cd app
YUNKA_REQUIRE_C114_QUALIFICATION=1 \
PROTOC="$(command -v protoc)" \
go test -timeout=5m -count=1 ./cmd/projectflow \
  -run '^TestC114QualificationRealBinaryFastFeedback$'
```

Normal local unit-test runs skip the expensive nested binary build unless the explicit qualification variable is set. Repository CI runs it automatically through the ordinary `app` test phase, so both `verify` and `verify-production` exercise the qualification path without introducing a second test implementation.

## Real engine identity proof

The qualification binary is built with:

```text
go build -buildvcs=true
```

The first successful generation must persist fast-feedback metadata whose engine identity is verified and begins with either:

- `vcs:` for a clean VCS-stamped build; or
- `module:` for a released module identity.

An unverified or dirty engine cannot satisfy the gate.

## Consumer proof

The disposable consumer contains:

- a Go module;
- a protobuf Domain/Application contract using the Yunka DSL options;
- a generated Yunka module;
- canonical Contract/Application/Assembly generated outputs;
- local disposable fast-feedback evidence.

The fixture exercises the same top-level commands developers use:

```text
yunka generate
yunka check
yunka generate --full
yunka check --full
```

No direct test hook or injected engine identity is used in the E2E proof.

## Required assertions

### First generation

The first `yunka generate --format json` must:

- succeed;
- execute canonical `contract`, `modules`, and `assembly` stages;
- not report `fast-generate`;
- create valid fast-feedback evidence with a verified engine identity.

### Fast hit

The next unchanged commands must report only:

```text
fast-generate / unchanged
fast-check    / ok
```

They must not pretend that canonical contract/module/assembly stages executed.

### Full escape hatch

Both:

```text
yunka generate --full
yunka check --full
```

must bypass fast evidence and execute the canonical stages.

### Corruption and recovery

After intentionally changing the generated contract manifest:

1. normal `yunka check` must miss the output fingerprint;
2. it must fall back to canonical validation;
3. it must fail with `YUNKA-DX-CONTRACT-002` rather than return a false fast hit;
4. normal `yunka generate` must run the canonical generator and repair the output;
5. refreshed evidence must remain verified;
6. subsequent generate/check calls must return to the fast path.

### Framework immutability

The tracked Yunka framework worktree must be clean before and after the qualification. Consumer files and local evidence live only under the disposable temporary fixture.

## Latency budget

For the tiny qualification consumer, each exact fast hit must complete within:

```text
2 seconds
```

This is deliberately stricter than the C11 developer-feedback target of 5–10 seconds while retaining headroom for shared CI scheduling, process startup, filesystem hashing, and protoc executable hashing.

The budget protects against accidentally reintroducing canonical compilation into the fast-hit path. It is a qualification budget for the tiny fixture, not a universal large-repository SLA.

## Non-goals

C11.4-D does not add:

- per-stage semantic cache;
- partial compiler execution;
- daemon/watch mode;
- background cache repair;
- cache mutation from `yunka check`;
- relaxed engine identity rules;
- changes to Contract, Module, Assembly, authorization, UoW, transaction, idempotency, or runtime semantics.

## Definition of done

- real VCS-stamped CLI binary qualifies;
- typed consumer first generation proves canonical path;
- unchanged generate/check prove fast hit;
- `--full` proves canonical bypass;
- output corruption proves fail-safe fallback and canonical C11.3 diagnostic;
- canonical generation recovers drift and refreshes evidence;
- fast path returns after recovery;
- each fast hit meets the 2-second tiny-fixture budget;
- tracked framework worktree remains unchanged;
- full CI, determinism, production/MySQL 8.4, and clean-worktree qualification pass on the exact head.
