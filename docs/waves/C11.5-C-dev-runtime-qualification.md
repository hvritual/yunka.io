## Goal

Qualify the complete C11.5 developer runtime path through the real CLI and real supervised OS processes. C11.5-C adds qualification evidence only; it does not add a supervisor, readiness protocol, runtime state model, or closure algorithm.

## Real qualification topology

The permanent qualification test builds two temporary binaries:

```text
qualified repository
    ├── go build -buildvcs=true -> yunka
    └── testdata runtime helper -> helper
```

It then creates a disposable consumer with:

```text
.yunka/project.json
    workflow.dev.manifest -> config/dev.runtime.json

.yunka/application-graph.json
    application:dependency
    application:app

config/dev.runtime.json
    schemaVersion: 3
    runtime.closure: true
    dependency process
        explicit argv
        explicit graphNode
        explicit loopback diagnostics readiness
    app process
        dependsOn: dependency
        explicit graphNode
        explicit loopback diagnostics readiness
```

The helper is not a framework runtime implementation. It is a test-only process that exposes the diagnostics JSON already expected by `pkg/devruntime` readiness and records start/ready/stop events. Yunka remains responsible for process launch, dependency barriers, readiness polling, report/graph persistence, signal handling, reverse shutdown, and closure validation.

## Qualification sequence

### 1. Bare happy path

Run:

```text
yunka dev --root <consumer> --target app
```

Required proof:

- no default `.yunka/dev.json` exists;
- C11.2 Project Profile therefore must locate `config/dev.runtime.json`;
- target `app` expands through the declared dependency to plan `dependency,app`;
- dependency reaches diagnostics readiness before `app` starts;
- app reaches diagnostics readiness;
- C11.5-B emits `DEV READY application=c115consumer`;
- canonical runtime report is `running` with both processes Ready and captured diagnostics.

### 2. Live closure evidence

While bare dev is still running:

```text
yunka dev status --root <consumer> --closure
```

This must pass the existing `devruntime.ValidateRuntimeClosure` path against the same plan/report/graph facts. C11.5-C introduces no closure checker.

### 3. Clean shutdown

Send SIGTERM to the real Yunka CLI. The canonical runner must:

- cancel supervision through the existing signal-aware context;
- stop processes in reverse handle order;
- leave both processes `stopped`;
- leave runtime report `state=stopped`, not `failed`.

The helper event log must prove:

```text
start:dependency
ready:dependency
start:app
ready:app
stop:app
stop:dependency
```

### 4. Explicit expert run equivalence

Repeat with:

```text
yunka dev run --root <consumer> --target app
```

The explicit expert command must resolve the same profile-backed manifest, produce the same plan, pass the same live closure status, and stop cleanly.

## Immutability proof

The qualification snapshots and rechecks:

- `.yunka/project.json`;
- configured `config/dev.runtime.json`;
- declared `.yunka/application-graph.json`;
- tracked Yunka repository worktree.

Only canonical runtime state/graph artifacts and test event/log files may change.

## Security boundary

All listener addresses are explicitly allocated by the qualification fixture and written into the DevManifest. The framework performs no port discovery. No secret or token is required by the helper readiness endpoint. Process argv remains developer-owned explicit manifest data and is not surfaced by C11.5-B evidence output.

## Definition of done

C11.5-C is qualified only when:

1. real Yunka CLI builds from the exact branch head;
2. non-default profile-backed DevManifest resolves through bare dev;
3. target/dependency ordering is proven by canonical report and external lifecycle events;
4. both application owners satisfy existing diagnostics readiness and captured diagnostics requirements;
5. bare dev reaches C11.5-B Ready evidence;
6. live `dev status --closure` passes existing closure validation;
7. SIGTERM produces reverse clean shutdown and final `stopped` runtime state;
8. explicit `dev run` repeats the same canonical behavior;
9. source profile/manifest/graph and framework tracked worktree remain unchanged;
10. exact-head full CI, determinism, production/MySQL 8.4 and clean-worktree gates pass.

## Local reproduction

On a Unix-like development environment:

```text
cd app
YUNKA_REQUIRE_C115_QUALIFICATION=1 go test -timeout=5m -count=1 ./cmd/dev -run '^TestC115QualificationRealDevRuntimeHappyPath$'
```

The test runs automatically when `CI=true`. Windows ordinary tests compile normally but the signal-specific qualification execution is skipped; the repository qualification authority remains the Unix CI runner.

## Non-goals

- no automatic port/listener discovery;
- no generated DevManifest;
- no watch/restart loop;
- no mock runner as final proof;
- no replacement for runtime report, Application Graph or closure validation;
- no C7-C10 semantic changes.
