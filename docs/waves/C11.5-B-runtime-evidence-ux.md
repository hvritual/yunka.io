## Goal

Make the normal `yunka dev` / `yunka dev run` path explain what is starting, when the canonical runtime becomes Ready, and where to inspect failure evidence without introducing another supervisor, readiness probe, health model, diagnostics store, or runtime state machine.

The UX layer is deliberately observational:

```text
DevManifest / Project Profile
        ↓
existing loadPlan
        ↓
existing pkg/devruntime.Run
        ↓
existing canonical RuntimeReport
        ↓
C11.5-B renderer
        ↓
plan / process state / Ready / failure guidance
```

## Canonical ownership

C11.5-B does **not** determine readiness itself.

The existing runner remains authoritative for:

- process dependency ordering;
- process start/stop/signal behavior;
- HTTP readiness probing;
- `diagnosticsReady` checks;
- readiness timeout/interval behavior;
- process `pending|starting|running|ready|failed|stopping|stopped` transitions;
- runtime `starting|running|stopping|stopped|failed` transitions;
- secret-free runtime report persistence;
- runtime graph persistence;
- closure validation.

The CLI only reads `RuntimeReport` written by that state machine.

## Developer output

Before launch, the happy path prints only the resolved process names:

```text
DEV plan processes=2 names=api,worker
```

It intentionally does **not** print argv, inherited environment values, readiness bearer tokens, runtime errors, DSNs, or secrets.

For runtime-enabled schema-v3 plans it also exposes the existing evidence locations:

```text
DEV evidence state=.yunka/dev-runtime.json graph=.yunka/runtime-graph.json
```

As canonical runtime reports change, the renderer may surface notable states:

```text
DEV STARTING process=api
DEV RUNNING process=api
DEV READY process=api
DEV READY application=yunka
```

The application-level `READY` line is emitted only after the existing runtime report reaches `state=running`. It is not inferred from process names, ports, elapsed time, or a second HTTP probe.

## Failure guidance

When the canonical runner returns a failure, the UX does not reproduce the raw runtime error text. The existing CLI error path still returns the actual error to the caller, while the evidence stream provides stable next actions:

```text
DEV FAILED process=api
DEV FAILED application=yunka
DEV inspect: yunka dev status --state .yunka/dev-runtime.json
DEV next: yunka doctor
```

Closure plans use the existing expert closure check:

```text
DEV inspect: yunka dev status --closure --state .yunka/dev-runtime.json
```

If no runtime report is available, the CLI does not invent one and only recommends the existing Doctor path.

## Legacy compatibility

Schema-v1/v2 plans do not enable the C10 runtime report model. C11.5-B therefore keeps their runner behavior unchanged and prints:

```text
DEV evidence runtime-report=disabled
```

No synthetic Ready signal is emitted for these plans.

## Security and determinism

The evidence renderer:

- prints process names, not process command arguments;
- prints project-relative canonical state/graph paths, not the absolute project root;
- does not print readiness URLs or token environment values;
- does not print `RuntimeReport.reason` or per-process error text;
- emits no timestamps;
- suppresses duplicate process/runtime states;
- preserves process stdout/stderr behavior unchanged.

## Definition of done

C11.5-B is complete only when:

1. bare `yunka dev` and `yunka dev run` still share the C11.5-A `runAction`;
2. `runAction` still uses `pkg/devruntime.Run` as the only supervisor;
3. runtime-enabled plans announce canonical state/graph evidence locations;
4. process Ready output is derived only from `ProcessRuntimeReport.state=ready`;
5. application Ready output is derived only from `RuntimeReport.state=running`;
6. failure guidance points to existing `dev status` / `doctor` paths;
7. legacy plans never receive synthetic Ready evidence;
8. command arguments, runtime error details, secrets and absolute project roots are absent from the evidence stream;
9. existing `dev plan`, `dev run`, `dev status`, target and closure interfaces remain compatible;
10. exact-head full CI, determinism, production/MySQL 8.4 and clean-worktree gates pass.

## Non-goals

- no new runner or daemon;
- no watch/restart loop;
- no second readiness HTTP client;
- no new health or closure algorithm;
- no process log persistence system;
- no automatic listener/port discovery;
- no environment/secret discovery;
- no replacement for `dev status` or `doctor`.
