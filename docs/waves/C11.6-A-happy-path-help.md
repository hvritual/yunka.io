## Goal

Make the already-qualified C11 developer workflow discoverable from root CLI help without changing command execution or prematurely deprecating expert interfaces.

The root help must make this path explicit:

```text
yunka init
    ↓
yunka generate
    ↓
yunka check
    ↓
yunka dev
```

## Taxonomy

Root commands are classified only for help/discovery:

### Developer workflow

- `init`
- `generate`
- `check`
- `dev`

These are the only commands presented as the normal C11 developer loop.

### Diagnostics and inspection

- `doctor`
- `inspect`
- `graph`

These expose evidence and troubleshooting paths already owned by existing diagnostics/graph implementations.

### Expert architecture

- `contract`
- `assembly`
- `module`
- `domain`
- `dependency`

These remain explicit expert escape hatches. C11.6-A does not rename, hide, remove, or deprecate them.

### Supplementary tooling

- `api`
- `doc`

Existing aliases and behavior remain unchanged.

## Implementation boundary

`applyDiscoverability` may modify only root `cli.App` discovery metadata:

- `Usage`;
- `Description`;
- `Command.Category`.

It must not modify:

- command names;
- aliases;
- flags;
- actions;
- subcommands;
- compiler/runtime behavior;
- project profile ownership;
- diagnostics semantics.

The existing root command construction remains intact. Discoverability metadata is applied only after the existing deterministic command-name sort.

## Developer-facing description

The root description explicitly includes:

```text
Start here with the developer workflow:

  yunka init -> yunka generate -> yunka check -> yunka dev
```

It also directs troubleshooting to `doctor/inspect/graph` and describes contract/assembly/module/domain/dependency as expert architecture interfaces.

No `deprecated` or `legacy` label is introduced because C11.6 does not yet define a removal/deprecation policy for those commands.

## Permanent tests

C11.6-A locks:

1. all 14 current root commands have one explicit category;
2. Developer workflow contains exactly `init`, `generate`, `check`, and `dev`;
3. applying discoverability does not change command inventory/order;
4. all assigned categories match the taxonomy;
5. root description contains the four-command path;
6. rendered urfave/cli app help contains all four categories and all root commands;
7. root help contains no unsupported deprecation/legacy language.

## Definition of done

C11.6-A is complete only when:

- the four-command path is visible in root CLI help;
- every existing root command remains visible;
- only four commands are categorized as Developer workflow;
- expert interfaces remain visible and behavior-compatible;
- no command/action/flag/subcommand behavior changes;
- deterministic help/inventory tests pass;
- full CI, Determinism, production/MySQL 8.4 and clean-worktree gates pass on the exact head.

- no new examples/reference pages yet; that belongs to C11.6-C;
- no command removal or deprecation;
- no compiler/runtime/config changes;
- no new source of architectural truth.
