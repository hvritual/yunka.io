# C11.2 — Project Profile

## Status

- State: **In progress**

- Parent wave: C11 Developer Experience Productization

## Goal

Make `.yunka/project.json` the narrow developer-workflow profile for project-local locations/defaults consumed by `yunka init`, `yunka generate`, and `yunka check`.

C11.2 does not introduce a second architecture or business DSL. The profile points to canonical facts; it does not redefine those facts.

## Ownership boundary

The profile may own only developer-workflow/location facts:

```text
.yunka/project.json
  ├─ database.tablePrefix                 existing project-local persistence convention
  └─ workflow
      ├─ contract.sources OR protoRoot    location only
      ├─ contract.generated               output location only
      ├─ modules.root                     module source location only
      ├─ generatedGo.root                 generated Go root location only
      ├─ generatedGo.import               optional import override only
      └─ dev.manifest                     dev-runtime manifest location only
```

The following remain forbidden in the project profile:

- Domain/Application/Operation declarations;
- Application/Operation dependency edges;
- authz/permission rules;
- transaction/UoW/idempotency policy;
- module capability or dependency declarations;
- AssemblyPlan relationships;
- process commands, readiness probes or runtime ownership facts from `.yunka/dev.json`;
- secrets or credentials.

## Schema evolution

C11.2 upgrades the existing database-only config from v1 to v2.

### Read semantics

`Load` accepts v1 and v2:

```text
v1 file
  -> decode legacy database prefix
  -> add v2 workflow defaults in memory
  -> validate v2 model
  -> return v2 Config
  -> DO NOT write the file
```

This is required so `yunka check`, `yunka generate`, tooling and AI inspection never mutate legacy project state merely by reading it.

### Explicit migration semantics

`yunka init` is the mutation boundary:

```text
v1 file
  -> load/migrate in memory
  -> preserve database prefix
  -> persist deterministic v2 JSON
```

A second `yunka init` with unchanged inputs must leave bytes unchanged.

## Profile-first resolution

C11.2 changes the happy-path resolver to:

```text
project root
   ↓
.yunka/project.json exists?
   ├─ yes -> load/validate profile
   │         ↓
   │         resolve exactly configured locations
   │         ↓
   │         missing configured source => FAIL CLOSED
   │
   └─ no  -> C11.1 conventional fallback
             contracts/sources.json OR contracts/proto
             contracts/generated
             modules
             internal
```

An explicit profile is authoritative for workflow locations. The resolver must never silently ignore a broken configured path and fall back to a conventional path that happens to exist.

## Generated Go import ownership

Preferred behavior:

```text
go.mod exists
  + generatedGo.root is project-local
      -> derive <go-module>/<relative-generated-root>
```

If the profile also supplies `generatedGo.import`, it must equal the safely derived value or resolution fails as a stale/conflicting duplicate.

If `go.mod` does not exist, an explicit import may be supplied for advanced consumer layouts.

The profile cannot use path escape for source/output roots. Expert commands remain the escape hatch for non-project-local arrangements.

## Compatibility

C11.2 preserves:

- C11.1 no-profile conventional resolution;
- top-level `yunka generate` and `yunka check` semantics;
- expert `yunka contract`, `yunka assembly`, `yunka module`, and `yunka dev` flags;
- C10 deterministic Contract/Application/Assembly output;
- all C7-C10 runtime/security/transaction owners.

## Permanent executable gates

C11.2 tests must prove:

1. fresh `yunka init` emits deterministic v2 profile defaults;
2. existing source inventory is selected explicitly at init time;
3. v1 profile loads as v2 without modifying bytes;
4. explicit init persists v1→v2 migration;
5. conflicting contract source declarations are rejected;
6. project-path escape is rejected;
7. explicit profile locations override conventions;
8. missing configured contract locations fail closed even when fallback paths exist;
9. generated Go import conflicts with `go.mod` fail;
10. explicit generated Go import works when `go.mod` is absent;
11. profiled custom-location typed Application/module generation produces Contract/Application/Assembly artifacts and passes `yunka check`;
12. existing C11.1 conventional happy-path and expert-equivalence tests remain green.

## Qualification gate

C11.2 is complete only when:

- all focused project/profile tests pass;
- full repository `make verify` passes;
- production/MySQL 8.4 `make verify-production` passes;
- determinism recheck passes;
- tracked worktree remains clean;
- no C7-C10 semantic owner is added to `.yunka/project.json`.

## Rollback

C11.2 is additive/backward-compatible. Rollback restores the v1 project-config reader and C11.1 conventional resolver. Existing expert compiler/runtime interfaces are unchanged.
