# C7.1 Static Module Catalog and Typed Bootstrap

## Status

Implementation subwave over the C6 baseline `7a37d289a3d8cc0fd22b599fef39afd02d563a54`.

## Developer-experience contract

C7 preserves the original framework's most valuable module ergonomics:

```go
import _ "example.com/service/modules/orders/autoload"
```

Adding a module remains one blank import. A module does not read root configuration, create database or RPC connections, or query a global service locator. It declares typed configuration and platform requirements, while the framework supplies shared capabilities and lifecycle ownership.

The preserved property is **zero dependency-acquisition code**, not zero dependency declaration.

## Static descriptor catalog

An autoload package may perform only one operation:

```go
func init() {
    modulecatalog.MustRegister(orders.GeneratedDescriptor())
}
```

The process-default catalog stores immutable descriptors only. It never stores App instances, configuration values, database handles, RPC connections, services, repositories, transactions, principals, or request scopes.

`Catalog.Seal()` rejects duplicate names, missing dependencies, cycles, and late registration. It produces a deterministic topological order independent of blank-import order. Tests and embedded applications may use isolated catalogs instead of the process default.

## Typed wiring seam

A descriptor contains:

- stable module name and version;
- explicit module dependencies;
- typed platform requirements;
- an ordinary Go `BuildFunc`.

`BuildContext` exposes only build-time capability providers for module configuration, logger, named GORM databases, event bus, and named typed gRPC connections. It is available only while constructing the module; business services do not retain a generic lookup context.

Generated wiring is ordinary Go and is checked by the compiler. Runtime field walking, `reflect.Value.Call`, and interface-implementation guessing are not part of the new path.

## Explicit App instances

`core.NewApp(AppOptions)` accepts a supplied catalog plus direct config/logger/database/event/RPC capabilities, or an advanced custom context factory. It seals the catalog, aggregates all config/database/event/RPC requirements, prepares shared capabilities once before any module build, then builds typed module instances in deterministic order and registers the capability owner plus modules with the existing Start/Health/Shutdown lifecycle. Named DB and RPC requirements are resolved once and each module receives a restricted view containing only its declared capabilities.

Multiple catalogs, factories, and App instances can coexist without sharing module runtime state. The new App path does not consume legacy global prepare/initiator lists, cannot mutate `globalConf`, and owns its RPC one-time registration independently.

The package-level legacy App remains temporarily active for unmigrated code. C7.1 introduces no new call sites to `GetApp`, global config/store APIs, reflective `Bind/Get/Put`, or lifecycle object pools. Those APIs remain scheduled for deletion in C7.3.

`framework/kernel.New` uses the process-default static catalog for the blank-import developer experience, while tests can pass an isolated catalog.

## Module generator

`yunka module --name orders` now generates:

```text
modules/orders/
├── config.go
├── dependencies.go
├── module.go
├── zz_yunka_module_gen.go
└── autoload/register.go
```

The generated module declares dependencies and receives them through typed wiring. The autoload package performs descriptor registration only.

## Architecture gate

The C7 architecture policy checks:

- autoload package name and shape;
- exactly one `init` function and one `modulecatalog.MustRegister` call;
- no autoload variables, types, I/O, environment reads, goroutines, or runtime composition;
- no `reflect` or `sync.Pool` in the typed catalog/kernel path;
- no calls to global service-locator APIs from the typed path.

## Compatibility and migration

C7.1 is additive. The old reflective container is not deleted until real modules are moved through C7.2. New modules use only the static catalog/typed path. No second generic container or indefinite global compatibility bridge is introduced.

## Rollback

Revert the single C7.1 commit. Because no existing module is forced onto the new path in this subwave, rollback restores the C6 composition baseline without data, wire, or runtime migration.
