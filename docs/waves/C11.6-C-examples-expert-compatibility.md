## Goal

Make the qualified C11 workflow easy to copy while permanently protecting the expert CLI surface from accidental breakage caused by discoverability work.

C11.6-C adds documentation and compatibility tests only. It does not add a new runtime, compiler path, project profile field, DevManifest field, DSL, or source of architectural truth.

## Canonical happy-path example

`docs/examples/c11-happy-path/` contains three files:

- `project.json` — valid Project Profile v2 shape;
- `dev.runtime.json` — valid schema-v3 DevManifest shape;
- `README.md` — the normal workflow and diagnostic/expert entry points.

The profile deliberately points to a non-default dev manifest:

```text
workflow.dev.manifest = config/dev.runtime.json
```

The DevManifest deliberately keeps the basic example small:

- schema version 3;
- one explicitly declared process;
- argv command array;
- one explicit HTTP readiness barrier;
- runtime state/graph evidence paths;
- closure disabled.

This demonstrates the C11.5 runtime evidence path without forcing Application Graph ownership/closure into every local project.

The values owned by an application remain explicit and replaceable by the consumer:

- process argv;
- readiness URL;
- runtime evidence paths.

Yunka does not infer those values from names, ports, source layout, or environment.

## Machine-validated examples

`app/cmd/examples_compatibility_test.go` validates the example files against the current canonical schemas:

- JSON decodes to `project.Config` and passes `project.Validate`;
- the Project Profile remains version 2 and uses exactly one contract source mode;
- the profile points to `config/dev.runtime.json`;
- the DevManifest is schema version 3 and passes `DevManifest.Validate`;
- the basic example does not require closure;
- the process has explicit readiness;
- the README contains the four-command happy path, runtime status, `yunka explain`, and all five expert help entry points.

The examples therefore fail CI if the canonical schema changes incompatibly without an intentional example update.

## Expert compatibility snapshots

C11.6-C protects the five root commands categorized as **Expert architecture**:

- `contract`;
- `assembly`;
- `module`;
- `domain`;
- `dependency`.

The compatibility test calls the real package `Command()` functions and snapshots only externally visible CLI shape:

- root command name;
- root command aliases;
- root flags, including flag aliases;
- whether a root action exists;
- subcommand names;
- subcommand aliases;
- subcommand flags, including aliases;
- whether a subcommand action exists.

It does **not** copy or reimplement the command actions themselves.

### Current protected surface

#### `contract`

Subcommands:

```text
lint
generate
check
diff
inspect
```

The snapshots protect the existing source/artifact/baseline/format flag surfaces.

#### `assembly`

Subcommands:

```text
generate
check
inspect
```

The snapshots protect source, module-root, output and typed assembly code flags.

#### `module`

The historical top-level compatibility action and `--name` flag remain protected.

Subcommands:

```text
new
check
```

The `new` snapshot includes capability/dependency flags such as config, logger, database, event bus, RPC and `depends-on`.

#### `domain`

Subcommands:

```text
new
generate
check
```

The existing short flag aliases (`-n`, `-o`, `-p`) are included in the compatibility surface.

#### `dependency`

Subcommand:

```text
check
```

The repository root, policy and Go-command flags remain protected.

## What the snapshot means

A snapshot failure does not mean an expert interface can never change. It means the change must be explicit and reviewed instead of arriving accidentally as part of help/docs work.

C11.6-C introduces no deprecation policy. No expert command is hidden, removed, renamed, or labeled legacy/deprecated.

## Definition of done

C11.6-C is complete only when:

1. a concise Project Profile + schema-v3 DevManifest example exists;
2. the examples are validated by canonical project/devruntime validators;
3. the documented normal workflow remains `init -> generate -> check -> dev`;
4. `yunka explain <CODE>` is shown as the diagnostic-code lookup path;
5. all five expert root commands remain visible and behavior-compatible;
6. expert command names, aliases, flags and subcommands are protected by snapshots built from the real `Command()` structures;
7. no runtime/compiler/config/diagnostic semantics are added or duplicated;
8. exact-head full CI, Determinism, production/MySQL 8.4 and clean-worktree gates pass;
9. permanent C11.4 fast-feedback and C11.5 dev-runtime qualification gates remain green.

## Non-goals

- no new developer command;
- no generated DevManifest;
- no command deprecation/removal;
- no freeze of internal implementation functions;
- no second Contract/Assembly/Module documentation truth;
- no closure requirement for the basic example;
- no runtime/compiler/config behavior changes.
