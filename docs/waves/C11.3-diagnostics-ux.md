# C11.3 — Diagnostics UX

## Status

- State: **In progress**
- Parent: issue #60 / C11 Developer Experience Productization
- Base: `main@335527711a81ef0f1a76077606192e8c4724f5f4`
- Delivery branch: `agent/c11-3-diagnostics-ux`
- Predecessors: C11.1 Happy Path and C11.2 Project Profile are qualified and merged

## Goal

Make developer-facing failures stable, actionable, and machine-readable without changing the canonical compiler/runtime semantics that produce those failures.

C11.3 introduces a common diagnostics presentation contract for developer workflows. It is an adapter/UX layer over existing facts and errors, not a new validation engine.

The target developer experience is:

```text
yunka check

ERROR YUNKA-DX-ASSEMBLY-001  assembly generated artifacts are stale
  stage:    assembly
  location: contracts/generated/assembly-plan.json
  cause:    generated bytes differ from canonical AssemblyPlan compilation
  action:   run `yunka generate`
```

and the same failure must be available as deterministic JSON for CI, IDEs and AI agents:

```json
{
  "schemaVersion": 1,
  "command": "check",
  "ok": false,
  "diagnostics": [
    {
      "code": "YUNKA-DX-ASSEMBLY-001",
      "severity": "error",
      "stage": "assembly",
      "summary": "assembly generated artifacts are stale",
      "location": {"path": "contracts/generated/assembly-plan.json"},
      "actions": [{"kind": "command", "value": "yunka generate"}]
    }
  ]
}
```

## Existing diagnostic surfaces

C11.3 must converge rather than discard useful existing structures:

1. `pkg/contract.Diagnostic` already carries contract-lint `severity`, semantic `path`, and `message`.
2. `pkg/devruntime.Check` already carries Doctor `name`, pass/warn/fail status, `detail`, and a remediation `action`.
3. C11.1/C11.2 `projectflow` currently add stage context through ordinary wrapped Go errors and stage reports.
4. Expert commands have established textual error messages and exit-code behavior that must remain compatible unless a specific DX change is explicitly qualified.

The common DX diagnostic contract should adapt these surfaces. It must not move contract lint rules, Doctor environment probes, Assembly drift logic, module checks, or runtime readiness logic into a new package.

## Diagnostic contract

Introduce one leaf-safe developer diagnostic model, preferably under `pkg/diagnostic` or another dependency-neutral package.

Minimum conceptual schema:

```go
type Diagnostic struct {
    Code     string
    Severity Severity
    Stage    string
    Summary  string
    Detail   string
    Location *Location
    Actions  []Action
}

type Location struct {
    Path   string
    Line   int
    Column int
    Ref    string
}

type Action struct {
    Kind  string
    Label string
    Value string
}
```

Required properties:

- deterministic JSON representation;
- no timestamps, request IDs, secrets, host-specific temporary paths or unbounded metadata by default;
- diagnostics ordered deterministically;
- stable externally meaningful `Code`;
- human summary separated from machine identity;
- remediation represented as structured actions, not only prose;
- optional source/artifact location;
- no executable action side effects: diagnostics describe actions but never auto-run them.

## Code stability

C11.3 diagnostic codes are public developer-tooling identities.

Preferred namespace:

```text
YUNKA-DX-PROJECT-xxx
YUNKA-DX-TOOLCHAIN-xxx
YUNKA-DX-CONTRACT-xxx
YUNKA-DX-MODULE-xxx
YUNKA-DX-ASSEMBLY-xxx
YUNKA-DX-DEV-xxx
```

Rules:

1. one code represents one stable failure class;
2. a code must never be silently reused for materially different semantics;
3. text may improve without changing the code;
4. codes are deterministic across text and JSON renderers;
5. raw underlying errors may appear in `detail`, but the diagnostic code is owned by the developer-facing boundary;
6. secrets and raw credential values must never enter diagnostics.

## C11.3 delivery slices

### A — Leaf diagnostic model and renderers

Introduce the dependency-neutral schema plus deterministic:

- validation/normalization;
- text rendering;
- JSON envelope rendering;
- severity ordering;
- action/location representation;
- tests proving stable bytes and absence of volatile fields.

This slice does not modify compiler/runtime validation semantics.

### B — `yunka generate` / `yunka check`

Upgrade the C11 Happy Path first because it is the primary developer loop.

Required behavior:

- add `--format text|json`;
- successful stage reports remain available;
- blocking project/profile/contract/module/assembly failures receive stable DX codes;
- existing canonical errors are retained as causes/details rather than discarded;
- `yunka check` remains read-only;
- `yunka generate` remains the only mutation path for generated artifacts;
- exit status remains non-zero for blocking errors in either renderer.

Priority first codes should cover at least:

- invalid/missing project profile paths;
- contract compile/lint failure;
- stale contract/application artifacts;
- module structure failure;
- assembly compile failure;
- stale assembly artifacts;
- missing/invalid generated Go import resolution.

### C — Doctor adapter

Preserve `devruntime.Doctor` as the environment-probe owner.

Adapt existing `Check{Name, Status, Detail, Action}` to the common diagnostic/output model so that:

- `yunka doctor` text remains concise;
- `yunka doctor --format json` uses the common envelope/schema where practical;
- existing pass/warn/fail semantics and `--strict` behavior are unchanged;
- recommended actions become structured actions;
- no environment mutation is introduced.

### D — Contract diagnostics adapter

Do not rewrite `contract.Lint` rules merely to gain DX codes.

Provide an adapter from existing `contract.Diagnostic{Severity, Path, Message}` into the common developer diagnostic model at CLI/workflow boundaries. Existing expert command behavior remains valid.

If adding codes directly to `contract.Diagnostic` proves necessary, it must be backward-compatible and separately tested; contract semantics must not depend on DX code strings.

### E — Qualification and compatibility

C11.3 is complete only after representative failures prove:

- text and JSON describe the same diagnostic identities;
- JSON bytes are deterministic for identical inputs;
- errors never contain secrets from project/runtime configuration;
- remediation actions are explicit and non-executing;
- legacy expert commands continue to work;
- `generate/check/doctor` exit behavior remains correct;
- full C7-C10 and C11.1/C11.2 qualification remains green;
- production/MySQL 8.4 and clean-worktree gates remain green.

## Expected change areas

Allowed/expected:

- a leaf-safe `pkg/diagnostic/**` package (final name subject to dependency proof);
- `app/cmd/projectflow/**`;
- `app/cmd/generate/**`;
- `app/cmd/check/**`;
- `app/cmd/doctor/**`;
- narrow Doctor/contract adapters;
- CLI tests and architecture tests;
- `docs/waves/**`.

Conditionally allowed:

- additive fields/helpers in `pkg/contract` or `pkg/devruntime` only when adapter-only composition cannot preserve existing semantics cleanly.

Forbidden:

- moving contract lint rules into DX code;
- moving Doctor probes into the CLI renderer;
- changing authorization, transaction/UoW, idempotency, Operation Executor, Platform or `core.App` semantics;
- new runtime diagnostics listener/protocol;
- auto-fix or command execution from remediation actions;
- secrets, tokens, DSNs or raw configuration values in machine-readable diagnostics;
- non-deterministic timestamps/IDs in deterministic command output;
- a second validation engine.

## Validation gate

C11.3 is qualified only when:

1. one shared diagnostic schema is used by the normal DX command surfaces;
2. stable codes are asserted by tests;
3. `generate/check` support deterministic `text` and `json` rendering;
4. representative project, contract, module and assembly failures produce actionable diagnostics;
5. Doctor participates without losing pass/warn/fail/strict behavior;
6. `check` remains read-only under failure;
7. expert command compatibility is preserved;
8. no secret leakage is possible through the structured schema under tested sensitive inputs;
9. full CI, determinism, production/MySQL 8.4 and clean-worktree gates pass on the exact head.

## Primary risks

### Risk 1 — diagnostic package becomes a second validation layer

**Control:** it owns schema/rendering/adaptation only. Canonical validators remain the source of truth.

### Risk 2 — unstable error-code taxonomy

**Control:** start with a small set of high-value failure classes; do not assign codes mechanically to every internal error.

### Risk 3 — JSON leaks implementation or secret details

**Control:** stable summary/location/action fields are explicit; raw cause text is sanitized/omitted when it may contain sensitive values.

### Risk 4 — machine format diverges from human behavior

**Control:** both renderers consume the same normalized diagnostic objects and tests assert identity equivalence.

## Rollback

Remove the common diagnostic adapters/renderers and restore the C11.2 textual CLI surfaces. Canonical compiler, project profile, Doctor probes and runtime behavior remain unchanged.
