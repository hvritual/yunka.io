## Goal

Define the smallest explicit deterministic AssemblyPlan that records which already-declared Applications, Operations, external bindings, static modules and platform requirements form one runnable Yunka application.

C10.1 is an ownership/IR wave. It does **not** generate runtime bootstrap code and does not introduce a new writable application DSL.

## Fact ownership

| Assembly fact | Canonical owner | C10.1 treatment |
| --- | --- | --- |
| Domain/Application identity | protobuf -> Contract Manifest | reused; never re-authored |
| Application `requires` | protobuf -> Contract Manifest / OperationPlan | reused; transitive closure derived |
| Operation identity | protobuf -> OperationPlan | reused |
| Operation `requires_operations` | protobuf -> OperationPlan | reused |
| HTTP binding | explicit protobuf HTTP binding -> OperationPlan | reference only; method/path are not copied as a new source |
| gRPC binding | protobuf service method -> OperationPlan | reference only; full method is not copied as a new source |
| Internal Operation exposure | absence of explicit external binding in OperationPlan | derived; no route/RPC is inferred |
| Module identity/version | static `modulecatalog.Descriptor` | reused through immutable descriptor snapshot |
| Module dependency | static `modulecatalog.Descriptor.DependsOn` | reused |
| Config/logger/database/event/RPC requirements | static module descriptor requirements | reused and expanded into a deterministic requirement inventory |
| Project DB table prefix | `.yunka/project.json` | remains project/domain persistence concern; not duplicated into AssemblyPlan v1 because bootstrap does not consume it |
| Local process argv/workdir/env/readiness | `.yunka/dev.json` | runtime-local; explicitly excluded from committed AssemblyPlan truth |
| Runtime health/route/RPC observations | Health/Diagnostics/Application Graph | observed runtime evidence only; not writable AssemblyPlan input |
| Root bootstrap target | C10.1 compiler convention | derived `root` target containing the complete selected inventory |

This matrix is normative for C10.1. A new field must identify its existing owner or prove that it is a genuinely new derived assembly fact before being added.

## AssemblyPlan v1

`pkg/assemblyplan` is a leaf-safe data/IR package. It deliberately has no dependency on `framework`, `gateway`, `app`, runtime registries, reflection, configuration providers, database clients, RPC clients, or service construction APIs.

The v1 plan contains:

- schema version and derived root identity;
- Application identities;
- direct Application dependency edges and deterministic transitive closure;
- Operation identities and their owning Application;
- direct internal Operation dependency edges;
- references to existing external HTTP/RPC bindings, not copied transport definitions;
- static module identities;
- direct module dependency edges;
- module capability requirement inventory;
- one derived `root` bootstrap target containing selected Applications/modules and the external/internal Operation partition;
- evidence on every entity/edge/reference classifying the fact as canonical, reused, derived, or runtime-local.

### Binding reference rule

AssemblyPlan does not own HTTP methods, paths or gRPC full method names. A binding reference contains only:

- Operation ID;
- transport kind (`http` or `rpc`);
- canonical binding index;
- evidence pointer into `operation-plans.json`.

C10.2 must resolve the reference against the same qualified OperationPlan before generating registration code. This prevents AssemblyPlan from becoming a competing API contract.

### Module boundary

`framework/core/modulecatalog.AssemblyInputs` converts an already-resolved static catalog plan into leaf-safe `assemblyplan.ModuleInput` values. Build functions and runtime providers never cross this boundary.

This preserves dependency direction:

```text
modulecatalog runtime descriptor
        |
        | snapshot immutable facts
        v
assemblyplan.ModuleInput
        |
        v
pkg/assemblyplan data IR
```

`pkg/assemblyplan` never imports `framework/core/modulecatalog`.

## Determinism and validation

AssemblyPlan normalization sorts all entity/edge/reference inventories and removes duplicate string inputs before validation. Canonical JSON is indented UTF-8 with one trailing newline. Digest is SHA-256 over those canonical bytes.

Validation fails closed for:

- unsupported schema version;
- empty/malformed Application identity;
- duplicate Applications, Operations or modules;
- unknown Application referenced by an Operation;
- unknown Application/module/Operation dependency endpoints;
- self-dependencies;
- Application/module/Operation dependency cycles;
- invalid or duplicate binding references;
- stale/incomplete Application dependency closure;
- stale/incomplete module requirement inventory;
- invalid requirement kinds/names;
- stale/incomplete root bootstrap target;
- missing provenance source/ref.

Internal Operations are those with zero explicit binding references. No transport is inferred from operation name, use-case name, HTTP verb conventions, package paths, method signatures or generated Go names.

## Compiler adapters

C10.1 introduces two one-way adapters:

1. `pkg/contract.CompileAssemblyPlan` converts Manifest + validated C9 OperationPlan + optional leaf-safe module inputs into AssemblyPlan input.
2. `framework/core/modulecatalog.AssemblyInputs` snapshots an already-resolved static catalog plan without exposing builders/providers/runtime objects.

The two adapters intentionally remain separate in C10.1. C10.2 owns final typed bootstrap compilation and decides where the qualified module snapshot and contract plan are joined.

## Current gate

The implementation must prove:

- deterministic canonical bytes/digest for reordered equivalent input;
- unknown Application reference fails closed;
- Application and module cycles fail closed;
- missing module requirement inventory fails closed;
- internal Operations retain zero binding references;
- Contract adapter references existing bindings without copying API definitions;
- module adapter exports immutable descriptor facts only;
- `go test ./...` in the existing `pkg` and `framework` modules covers the new package/adapters through the normal repository verification path.

## Deferred to C10.2

C10.1 does not:

- generate `core.App` or `kernel.New` bootstrap code;
- instantiate Platform Providers;
- register REST/gRPC servers;
- start processes;
- change `yunka dev`;
- select product-specific subsets of Applications/modules;
- add a second project/runtime configuration file;
- migrate `hvritual/biz`.

If C10.2 requires multiple independently selectable bootstrap targets, that selection must first identify a canonical owner. C10.1 v1 deliberately uses one derived `root` target instead of inventing a new target-selection DSL.

## Rollback

C10.1 is independently removable: delete `pkg/assemblyplan`, the two read-only adapters, their tests and this document. No C9 runtime behavior, contract semantics, authz, ExecutionScope, transaction, RPC, REST, or dev-runtime behavior changes.
