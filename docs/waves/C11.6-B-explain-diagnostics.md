## Goal

Make every currently registered stable C11.3 `YUNKA-DX-*` identity directly discoverable from the CLI without creating a second error taxonomy, validator, documentation crawler, or runtime inference path.

```text
existing validators/adapters
        ↓
pkg/diagnostic Definition catalog
        ├─ projectflow diagnostics
        ├─ Doctor diagnostics
        ├─ CLI format diagnostics
        └─ yunka explain <CODE>
```

## Canonical ownership

`pkg/diagnostic` already owns stable developer-facing diagnostic identity. C11.6-B makes that ownership explicit through a canonical `Definition` catalog containing only durable static presentation facts:

- stable code;
- stage;
- concise meaning;
- static project-relative location when one exists;
- static non-executing remediation action when one already exists.

The catalog does **not** contain dynamic validation facts. Contract/compiler errors, module validation detail, Assembly drift detail, Doctor environment observations, and current-environment Doctor remediation text remain with their existing owners.

Existing producers are changed to reference the catalog for static identity instead of maintaining parallel code/stage dictionaries. `yunka explain` is therefore a read-only view of the same identity source used by production diagnostics.

## Command

```text
yunka explain <CODE>
yunka explain <CODE> --format json
```

Example:

```text
yunka explain YUNKA-DX-CONTRACT-002
```

Text output is deterministic:

```text
YUNKA-DX-CONTRACT-002
  stage:    contract
  meaning:  generated contract artifacts are stale
  action:   Regenerate: yunka generate
```

JSON output uses a versioned envelope with the canonical Definition.

## Lookup rules

Lookup normalization is deliberately conservative:

1. trim surrounding whitespace;
2. normalize case to uppercase;
3. perform an exact catalog lookup.

There is no fuzzy search, prefix guessing, edit-distance matching, alias table, AI-generated explanation, or fallback to a similar code.

Unknown codes return a stable non-zero result. JSON mode returns a machine-readable unknown-code envelope and never attaches an invented Definition.

## Remediation safety

Definition actions reuse the C11.3 structured `diagnostic.Action` contract. They are descriptive data only. `yunka explain` has no execution path for an action value and never runs commands or edits files.

Doctor remediation remains dynamic because it can depend on the current environment. The Doctor adapter still produces that action at runtime; the Definition catalog owns only the Doctor diagnostic identity/stage/static location.

## Existing producers

C11.6-B converges these static identities onto the catalog:

- `projectflow.Diagnose`;
- Doctor check adapter code/stage/location mapping;
- unsupported-output-format diagnostics used by `generate/check/doctor/explain` presentation paths.

Existing runtime diagnostic output remains behavior-compatible. Permanent tests require projectflow summaries/actions and Doctor mapping identities to resolve through the same Definition catalog.

## Root discoverability

`explain` is added to the existing **Diagnostics and inspection** category. The C11.6-A developer workflow remains exactly:

```text
init -> generate -> check -> dev
```

No expert command is removed, renamed, hidden, or deprecated.

## Permanent tests

C11.6-B locks:

1. catalog definitions are unique, valid and code-sorted;
2. catalog lookup performs trim/case normalization only;
3. catalog action slices cannot be mutated through returned copies;
4. `projectflow.Diagnose` remains equivalent to the catalog identity;
5. every current Doctor probe maps to a registered Definition;
6. known-code text explanation contains canonical stage/meaning/action;
7. known-code JSON is deterministic and machine-readable;
8. unknown codes never fuzzy-match another Definition;
9. unknown JSON has non-zero truth and no Definition;
10. unsupported explain format reuses `YUNKA-DX-DEV-001`;
11. root help keeps explain in Diagnostics while Developer workflow remains exactly four commands.

## Definition of done

C11.6-B is complete only when:

- `yunka explain <CODE>` and `--format json` work from the real root CLI;
- existing diagnostic producers reference the canonical catalog for stable identity;
- no duplicate explain-only code/stage dictionary exists;
- unknown codes fail closed without guessing;
- remediation remains non-executing;
- existing generate/check/doctor diagnostic output remains compatible;
- C11.4/C11.5 permanent real-CLI qualification gates remain green;
- exact-head full CI, Determinism, production/MySQL 8.4 and clean-worktree gates pass.

## Non-goals

- no fuzzy search;
- no full-text search;
- no remote/web documentation lookup;
- no AI explanation at runtime;
- no remediation execution;
- no new validator/error taxonomy;
- no compiler/runtime/config ownership changes;
- no command removal/deprecation.
