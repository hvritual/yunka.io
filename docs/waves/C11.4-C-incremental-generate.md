## Goal

Reduce repeated `yunka generate` latency without creating a second compiler or partial semantic cache.

C11.4-C deliberately starts with a conservative whole-pipeline no-op optimization:

```text
resolve project
   ↓
load qualified fast-feedback evidence
   ↓
recompute current engine/toolchain/input/output fingerprints
   ↓
exact verified reusable hit?
   ├─ yes → return explicit `fast-generate` no-op success
   └─ no  → execute canonical full Generate, then best-effort refresh evidence
```

No stage is partially regenerated from cached semantic output. A cache hit proves the existing generated outputs already correspond to the exact qualified inputs, engine and toolchain, so doing nothing is byte-equivalent to a full deterministic generation.

## Safety rules

- `projectflow.Generate` remains the authoritative full generation implementation.
- The fast wrapper may skip generation only when `fastfeedback.Reusable(cached, current)` is true.
- Missing, corrupt, unsupported or unverifiable evidence is a miss, never an error.
- Dirty/unverified engine identity is a miss.
- Engine, protoc/toolchain, project profile, go.mod, contract sources/proto paths, module root or generated output mismatch is a miss.
- A miss always executes canonical full Generate.
- After a successful canonical fallback, fresh evidence may be recorded best-effort.
- Evidence refresh failure cannot turn a successful generation into failure.
- Exact-hit no-op must not rewrite generated artifacts or cache metadata.
- `yunka generate --full` must always execute canonical full generation and refresh evidence best-effort.
- Text/JSON output must clearly identify `fast-generate` and must not pretend contract/module/assembly stages were executed.

## Why whole-pipeline no-op first

C11.4-A currently provides a single canonical input fingerprint and a single conservative generated-output fingerprint. Using those proofs to skip the entire pipeline on an exact hit is safe and directly provable.

Introducing per-stage cache reuse before a canonical stage-owned input/output inventory exists would create several risks:

- duplicated dependency logic between Contract, Module and Assembly stages;
- stale cross-stage dependencies;
- hidden ordering/preference semantics;
- a second source of truth for generated-file ownership.

Stage-granular incremental generation can be considered later only after a qualified per-stage evidence contract exists. It is not required for C11.4-C.

## Definition of done

- top-level `yunka generate` uses a fail-safe incremental wrapper;
- exact verified hit bypasses canonical Generate and performs zero filesystem writes;
- hit returns deterministic `fast-generate` text/JSON output;
- missing/corrupt/unverified/mismatched evidence executes canonical Generate;
- canonical fallback refreshes evidence best-effort only after generation succeeds;
- output drift/missing generated files forces canonical regeneration rather than no-op;
- `--full` forces canonical generation;
- expert/internal calls to `projectflow.Generate` remain behavior-compatible;
- tests prove exact-hit bypass, fallback, output recovery, read/write behavior and full escape hatch;
- full CI, determinism, production/MySQL 8.4 and clean-worktree gates pass on exact head.
