# C4.1 Module Publication Convergence

## Goal

Make Yunka's publishable Go modules independently consumable outside the repository workspace.

## Canonical module identities

- `github.com/hvritual/yunka.io/pkg`
- `github.com/hvritual/yunka.io/framework`
- `github.com/hvritual/yunka.io/gateway`

`app` remains the repository-owned developer/tooling module and is not part of the public module release set.

## Dependency order

`pkg -> framework -> gateway`.

Publishable module `go.mod` files must not contain local `replace` directives. The repository `go.work` is only a development composition surface and is not a release contract. `go work sync` is deliberately excluded from release qualification because it can project workspace-wide MVS selections back into otherwise independent modules.

## Compatibility decision

The repository-owned module that impersonated `github.com/go-kit/kit` is removed from the release graph. The Aliyun SLS SDK's historical `github.com/go-kit/kit/log` imports resolve through the actual upstream Go kit module instead of a consumer-invisible local replacement.

## Qualification

C4.1 is qualified only when the exact tagged candidate passes:

1. source-workspace `test/vet/build` with all four repository modules;
2. each publishable module's `GOWORK=off test/vet/build`;
3. no publishable `go.mod` contains `replace`;
4. a clean external consumer fetches the same release version of pkg/framework/gateway.

The first qualification release is `v0.1.0-c41rc5`; failed qualification deletes the RC tags. Stable tags are created only after canonical integration.

## RC2 dependency convergence

RC1 validated the GitHub multi-module identity and tag layout, but removing the
repository-local go-kit compatibility module exposed the historical
`github.com/go-kit/kit v0.10.0` dependency graph. That graph reaches the removed
`github.com/lyft/protoc-gen-validate v0.0.13` repository through old Zipkin/gRPC
dependencies. RC2 raises `github.com/go-kit/kit` to `v0.13.0`, which preserves
the legacy `kit/log` and `kit/log/level` compatibility packages used by the
Aliyun SLS SDK while using the maintained dependency graph. No local `replace`
is added to any publishable module.

## RC3 genproto split convergence

RC2 removed the unreachable Lyft dependency by raising Go kit to v0.13.0.
That version still references a 2021 pre-split root `google.golang.org/genproto`,
while Yunka already uses the modern split `googleapis/api` and `googleapis/rpc`
modules. The mixed graph produces ambiguous imports.

A plain modern root-genproto `require` is not stable because `go mod tidy`
removes version-only constraints that have no package dependency. RC3 therefore
adds `pkg/internal/dependencyanchor`, enabled only by the
`yunka_dependency_anchor` build tag, with a blank import of the root-module-only
`google.golang.org/genproto/googleapis/type/date` package. This gives the modern
root genproto floor a real package reason to remain in `pkg/go.mod`; Go's module
tidy analysis considers build-tagged packages, while normal Yunka runtime builds
do not compile the anchor. Framework and gateway inherit the floor transitively
through their published dependency on pkg. No publishable module uses `replace`.

## RC4 protobuf regeneration

RC3 made the dependency graph independently resolvable and tidy-stable, then
exposed a generated-artifact defect in gateway RPC initialization. The initial
C4.1 path migration text-replaced module paths inside generated `.pb.go` raw
descriptor literals. Those literals are length-delimited protobuf binary data,
so increasing the embedded `go_package` path length without regeneration
corrupted descriptor framing and caused `google.golang.org/protobuf` to panic
in `unmarshalSeed`.

RC4 aligns the RPC generator's canonical module prefix with
`github.com/hvritual/yunka.io` and regenerates all managed protobuf Go outputs
from canonical `.proto` sources using the repository-locked protoc and Go
plugins. The generator is run directly before publication so descriptor repair
does not depend on a not-yet-existing RC version. Contract generation and full
compatibility checks run only after the exact RC4 tags exist.

## RC5 qualification hygiene

RC4 proved the independently published dependency graph, canonical RPC
generator identity, protobuf descriptor regeneration, contract generation,
and pkg/framework/gateway workspace tests. It then exposed two app-level
qualification hygiene defects rather than a publication defect.

First, main already contains the declarative `module add`, `module require`,
and `module show` commands from runtime-composition convergence, while the
C11.6 expert CLI snapshot still described the earlier `check/new` surface.
RC5 updates that baseline snapshot to the command surface already present on
main.

Second, earlier C4.1 candidate preparation deleted tracked `go.work.sum`.
Subsequent workspace commands recreated it as an untracked file. The C11.4
test's pre-build clean check intentionally ignored untracked files, while Go
VCS stamping observed the repository as modified and emitted
`vcs.modified=true`, making fast-feedback engine evidence unverified.

RC5 performs pre-publication source qualification through a runner-external
go.work that uses the same four repository modules plus version-specific
local replacements for sibling release edges. This handles Go workspace MVS
loading of versioned inter-module requirements without putting any local
replace in publishable go.mod files or the repository go.work. The temporary
workspace sum is copied back as tracked go.work.sum, so ordinary workspace
commands no longer create an untracked VCS-dirty artifact.

Fresh sibling RC versions are not resolved remotely before publication.
Exact GOWORK=off tidy/resolution starts only after RC5 tags point to the
committed candidate. App remains repository-owned tooling and is qualified
in source-workspace mode; standalone release qualification is limited to
pkg/framework/gateway.

## RC7 clean repository qualification

RC6 proved the dependency-ordered module publication itself: pkg,
framework-on-pkg, and gateway-on-framework/pkg all passed independent
GOWORK=off tidy/test/vet/build. RC6 then failed only because app/root
bookkeeping changes were left uncommitted while the C11.4 fast-feedback
qualification correctly required a clean tracked worktree.

RC7 keeps the same staged publication model and makes repository-owned app
convergence explicit bookkeeping. After all three module tags exist, app is
pinned to the real pkg release, root go.work.sum is rebuilt from the tagged
graph, generated/contract outputs are checked, and those repository changes
are committed before any app VCS-identity qualification runs. This preserves
`vcs.modified=false` as an actual invariant instead of weakening the test.
