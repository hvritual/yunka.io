### C10.4-P1-001 — post-Platform typed runtime binding

Real Biz exposed one generic structural gap.

The canonical Biz `operation.Executor` requires the App-owned `primary` database for:

- Access/IAM authorization data;
- GORM transaction factory;
- durable Operation idempotency state.

That database intentionally does not exist until:

```text
kernel.New
  -> core.NewApp
  -> Platform.Prepare
```

C10.3's generated `BootstrapOptions` originally required `ApplicationFactories` and `Executor` before Bootstrap, which would have forced the consumer either to open a duplicate database outside Platform ownership or to introduce a hidden lazy side channel.

C10.4 added the smallest generic seam:

```go
type RuntimeBindings struct {
    Factories ApplicationFactories
    Executor  operation.Executor
}

type RuntimeBinder func(context.Context, *platform.Provider) (RuntimeBindings, error)
```

Generated Bootstrap now supports:

```text
NewCatalog
  -> kernel.Bootstrap
     -> kernel.New / Platform.Prepare
     -> Build callback
        -> explicit consumer RuntimeBinder(prepared Platform)
        -> generated BuildApplications
     -> generated RegisterTransports
     -> existing core.App.Start
```

The prebuilt Factories/Executor path remains available and compatible.

Permanent architecture rules ensure the binder:

- does not call `Platform.Prepare`;
- does not create a new Platform;
- does not use reflection/service lookup;
- does not own authorization semantics;
- does not own transaction/UoW semantics;
- does not own lifecycle;
- does not fall back to the process-global default module catalog.

**Disposition:** **C10.4-P1-001 CLOSED.**

## Before / after structural plumbing

### Before C10.4

`cmd/biz/main.go` manually:

- selected module autoload/default catalog;
- called `kernel.New`;
- started/shut down the App outside generated assembly.

`modules/deviceops/module.go` manually:

- constructed canonical Executor dependencies;
- constructed handwritten Applications;
- constructed generated child capabilities;
- registered canonical REST Operations;
- registered canonical gRPC Operations;
- opened listeners/servers;
- owned server health bookkeeping;
- owned graceful server shutdown.

### After C10.4

Generated `internal/assembly` owns:

- explicit module catalog composition;
- deterministic Application dependency build order;
- generated typed child capability construction;
- canonical REST registration;
- canonical gRPC registration;
- runtime route/RPC inventory;
- typed Bootstrap into existing kernel/core lifecycle.

Real Biz `modules/deviceops.Module` is reduced to its descriptor/capability participant role and no longer owns process runtime wiring.

Real Biz `internal/bizruntime` intentionally owns only consumer facts and adapters:

- process config/secrets;
- database config;
- migration/bootstrap policy;
- bearer authentication adapter;
- Device OperationGuard and product scope interpretation;
- construction of the existing canonical C9 Security/Executor;
- repository and handwritten Application constructors;
- explicit listener addresses.

It supplies those facts via generated `RuntimeBinder`; it does not construct child capabilities or register canonical transports.

HTTP/gRPC servers are caller-created explicit resources adapted by existing `framework/runtimecomponent`, and the same `core.App` owns their Start/Health/Shutdown lifecycle.

Biz `/healthz` now adapts `core.App.Health` rather than maintaining independent module health semantics.
