## Purpose

C10.5 is the release qualification and fact-reconciliation wave for the complete C10 Runtime Assembly stack. It does not add product or framework features.

The objective is to prove that the exact release candidate is deterministic, production-verifiable, consumable by the real Biz application, and internally consistent across code, generated artifacts, documentation, durable memory, and Framework Pressure records.

## Non-goals

C10.5 must not introduce:

- a second runtime or lifecycle owner;
- reflection-based dependency injection or a service locator;
- a second writable assembly DSL;
- transport/path inference;
- duplicate authorization or transaction ownership;
- generic BPMN/workflow or distributed transaction/2PC;
- generic SQL/data-scope policy;
- framework-owned business resource taxonomy;
- audit/cache semantics, idempotency response replay, or Saga topology expansion;
- business-semantic inference or Biz-specific framework behavior.

A release-blocking defect is not permission to expand scope. The smallest correctness fix must be separately classified and permanently tested.

## Release candidate invariants

The exact C10 release candidate must preserve:

- protobuf as the canonical writable Contract source;
- deterministic immutable AssemblyPlan facts;
- generated typed Application construction and dependency wiring;
- generated typed local child capabilities through canonical C9 `ExecuteChildTyped`;
- canonical C9 Executor/ExecutionScope authorization, idempotency, and transaction semantics;
- `core.App` as the single lifecycle owner;
- `platform.Provider` as App-owned shared capability owner;
- generated explicit REST/gRPC registration only from declared bindings;
- internal-only Operations remaining transport-free;
- safe Diagnostics/Application Graph evidence;
- explicit `yunka dev --closure` ownership/readiness semantics;
- post-Platform `RuntimeBinder` as a typed construction seam only, never a second runtime.

## Exact release gate

C10.5 is qualified only when one exact candidate tree passes all of the following.

### A. Predecessor and fact reconciliation

1. Confirm C10.1-C10.4 qualified heads and dependency order.
2. Confirm active wave docs, `PROJECT_MEMORY.md`, Issue/PR status, and Framework Pressure records agree with the code tree.
3. Confirm no stale generated artifact or stale migration path is represented as current truth.

### B. Framework determinism and production gate

4. Run canonical framework generation/check paths on the exact candidate and require no tracked drift.
5. Run `make verify-production` with the locked Go/protoc toolchain and MySQL 8.4.
6. Require architecture, contract, Assembly, C10.2, C10.3, test, race, vet, vulnerability, build, and MySQL integration gates to pass.
7. Require final framework tracked worktree clean.

### C. Real-consumer qualification

8. Checkout exact `hvritual/biz` qualified C10 consumer truth against the exact framework candidate.
9. Run Biz `make generate` twice.
10. Require byte-for-byte second-generation zero drift for canonical Contract/Assembly artifacts.
11. Run Biz `make verify`.
12. Run Biz MySQL 8.4 `make pressure`.
13. Re-prove internal-only Operation non-exposure, explicit permission closure, one root authorization, one root UoW/shared child scope, and generated transport registration.
14. Require final Biz tracked worktree clean.

### D. Architecture regression audit

15. Verify no reflection DI, generic service lookup, package scanning, command/listener inference, or second lifecycle owner was introduced.
16. Verify no direct transport bypass of the canonical C9 Executor.
17. Verify no Application-level duplicate authorization or root transaction sequencing.
18. Verify no business-specific scope/semantics migrated from Biz into Yunka merely for code reduction.

### E. Release reconciliation

19. Reconcile code, generated artifacts, documentation, durable memory, and Framework Pressure dispositions against executable evidence.
20. Produce a stack-merge readiness assessment identifying exact heads, PR order, rollback points, and any remaining deferred pressure.

## Completion and merge boundary

C10.5 may be marked **Complete / Qualified** only on an exact head covered by executable evidence for every release gate above.

C10 qualification does **not** authorize merge. C10.1-C10.5 PRs remain subject to ordered review/merge, and `main` must not move without explicit user authorization.

## Rollback

Until the C10 stack is explicitly merged, the qualified predecessor branches and real Biz C9.9/C10.4 heads remain immutable rollback points. Release qualification must not force-update or destroy those evidence carriers.
