## Goal

Compile the C10.1 AssemblyPlan and the existing canonical type-resolution facts into deterministic typed Go composition. Generated code owns structural wiring only; handwritten code continues to own all business behavior.

## First compiler slice

The first slice establishes one deterministic compiler path:

```text
PB Contract / Manifest
        |
        v
canonical OperationPlan
        |
qualified module snapshot
        |
        v
CompileAssembly
        |
        +--> contracts/generated/assembly-plan.json
        |
        +--> assembly/zz_yunka_assembly_gen.go
```

The plan and typed Go are produced from the same joined fact set. They are not generated through independent pipelines.

## Generated structural surface

The generated assembly package currently owns:

1. `ApplicationFactories` — a generated Go interface with one required factory method for every declared Application;
2. `<Application>Dependencies` — typed dependency values for direct `ApplicationDeclaration.requires` edges;
3. `Applications` — typed built Application inventory;
4. `BuildApplications` — deterministic dependency-order construction;
5. existing C9 `New<Dependency>ChildCapability` calls for local child-Operation wiring;
6. `KernelDependencies` / `KernelOptions` — a typed seam into the existing kernel, without calling `kernel.New`;
7. `ExpectedModuleRequirements` — the deterministic aggregate module/capability requirement evidence compiled from AssemblyPlan;
8. `TransportBindings` / `RegisterTransports` — deterministic calls into existing C9 REST/gRPC generated registrars only for explicit external binding references;
9. `AssemblyPlanDigest` — binds generated Go to the exact AssemblyPlan bytes used by the compiler.

The generated factory surface is an interface rather than a string map or registry. A handwritten provider that omits any Application factory does not satisfy the generated interface at Go compile time.

## Transport rule

C10.2 does not generate another transport runtime.

For each Application:

- HTTP registration is emitted only when its canonical AssemblyPlan Operations contain at least one `http` binding reference;
- gRPC registration is emitted only when its canonical AssemblyPlan Operations contain at least one `rpc` binding reference;
- the generated code delegates to the existing C9 `RegisterOperationExecutor` / multi-Application equivalent;
- an internal-only Operation produces no REST or gRPC registration;
- C9 OperationPlan/Executor security, transaction, idempotency, and child execution semantics remain authoritative.

## Application dependency rule

Application construction follows a deterministic topological order from explicit `ApplicationDeclaration.requires` facts.

For a dependency such as:

```text
device/transfer -> site/query
```

C10.2 generates structural wiring equivalent to:

```text
site/query factory
    ↓
site/query Application
    ↓
existing C9 NewSiteQueryChildCapability(target, executor)
    ↓
device/transfer Dependencies
    ↓
device/transfer factory
```

No direct cross-Application repository lookup or service locator is introduced.

## Kernel and module boundary

C10.2 currently generates a typed kernel/catalog seam and the expected module requirement set, but it does **not** infer Go package imports for modules from module names.

The current module descriptor owns runtime descriptor facts (`Name`, `Version`, `DependsOn`, capability requirements, `Build`) but does not retain a canonical Go import-path/symbol fact in AssemblyPlan. Deriving `framework/modules/<name>` from the module name would be implicit package-name activation and is forbidden by the C10 roadmap.

Therefore explicit static module descriptor Go composition remains open inside C10.2 until one of these is proven:

1. an existing canonical module import/symbol owner can be reused; or
2. real compiler pressure proves the smallest new explicit module codegen-binding fact, reviewed separately.

This is not permission to add a second module config file.

## Artifact ownership

- `contracts/generated/assembly-plan.json` is now emitted by `CompileAssembly` / `WriteAssemblyCompilation`, after Contract/OperationPlan and qualified module snapshot are joined.
- `assembly/zz_yunka_assembly_gen.go` is the generated typed structural output below the supplied code root.
- `CheckAssemblyCompilation` verifies both artifacts against the same compilation result.
- second generation must be byte-for-byte zero drift.

## Architecture constraints

Permanent architecture policy rejects C10.2 regressions toward:

- reflection DI;
- package/plugin discovery;
- runtime filesystem scanning;
- service locator or string-keyed Application registry;
- `kernel.New` / process start inside the compiler-generated structural layer;
- inferred module Go import paths from module names.

## Explicit non-goals

C10.2 does not:

- generate business use-case implementations;
- generate business invariants, state machines, semantic mapping, or queries;
- add reflection/service locator/runtime package scanning;
- add a new authorization or execution phase;
- add a new transaction/UoW/idempotency implementation;
- start `core.App` or processes;
- implement health/readiness/diagnostics/dev-runtime closure (C10.3);
- migrate the real Biz consumer (C10.4).

## Rollback
