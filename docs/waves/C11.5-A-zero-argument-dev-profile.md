## Goal

Make bare `yunka dev` the normal developer entry point while preserving the existing C10 devruntime implementation and explicit expert subcommands.

The happy path becomes:

```text
yunka dev
    ↓
resolve project root
    ↓
resolve dev manifest location
    ↓
load the existing explicit DevManifest
    ↓
build the existing devruntime Plan
    ↓
run the existing devruntime supervisor
```

There is no new planner, process model, readiness model, supervisor, or runtime report format in C11.5-A.

## One run action

Bare:

```text
yunka dev
```

and explicit:

```text
yunka dev run
```

must reference the same `runAction` function. The parent command does not copy or wrap supervisor logic.

The explicit subcommands remain:

```text
yunka dev plan
yunka dev run
yunka dev status
```

## Project Profile resolution

C11.2 already gives `.yunka/project.json` ownership of one dev-related fact only:

```text
workflow.dev.manifest
```

C11.5-A makes that location effective for dev commands.

Resolution precedence is:

```text
explicit --config
        ↓ otherwise
valid project profile workflow.dev.manifest
        ↓ otherwise when profile is absent
.yunka/dev.json
```

Rules:

- explicit `--config` wins without requiring project-profile parsing;
- a present but invalid profile fails closed when the implicit default depends on it;
- an absent profile preserves the historical `.yunka/dev.json` convention;
- a legacy v1 project profile is upgraded in memory through the existing C11.2 loader and therefore resolves `.yunka/dev.json` without writing the profile;
- all resolved relative manifest paths remain rooted through the existing CLI path logic.

## Ownership boundary

The project profile owns only **where the DevManifest is located**.

The DevManifest remains sole owner of:

- process names;
- argv commands;
- working directories;
- dependencies;
- graph nodes;
- inherited environment variable names;
- readiness URLs/timeouts/statuses;
- diagnostics-ready/capture requirements;
- runtime application/state/graph/contract paths;
- shutdown timeout;
- closure mode.

C11.5-A must not copy any of these facts into `.yunka/project.json`.

## Compatibility

Existing expert forms remain valid:

```text
yunka dev plan --root ... --config ... --target ...
yunka dev run --root ... --config ... --target ...
yunka dev status --root ... --config ... --closure ...
```

Bare `yunka dev` exposes the same run-oriented common flags:

```text
--root
--config
--graph
--target
--closure
```

The parent and `run` subcommand deliberately share the same action implementation.

## Non-goals

C11.5-A does not:

- change `pkg/devruntime.Run`;
- infer processes from generated applications;
- infer listener addresses or secrets;
- auto-create `.yunka/dev.json`;
- duplicate runtime facts into `.yunka/project.json`;
- change readiness or closure validation;
- change `dev status` report semantics;
- add background/daemon process behavior.

## Definition of done

- bare `yunka dev` has a canonical run action;
- bare `dev` and explicit `dev run` reference one shared action;
- parent command exposes run happy-path flags;
- profile `workflow.dev.manifest` is used when `--config` is implicit;
- explicit `--config` wins;
- absent profile preserves `.yunka/dev.json`;
- invalid profile fails closed for implicit config;
- legacy profile resolution is read-only;
- `loadPlan` is proven against a custom profile manifest path;
- existing plan/run/status closure tests remain green;
- full CI, determinism, production/MySQL 8.4, and clean-worktree qualification pass on exact head.
