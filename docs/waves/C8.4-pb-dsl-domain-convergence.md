# C8.4 — PB DSL and Domain Compiler Responsibility Convergence

## Status

- State: **Planned**
- Planning baseline: `main@d18109cfd516b052629e62cbcfd5866b8c1c9276`
- Precondition: C8.3 Permission authorization convergence is complete.
- Delivery model: four independently reviewable subwaves, followed by one final convergence gate.

## Decision summary

C8.4 establishes two explicit and non-overlapping source-of-truth boundaries:

```text
Protobuf owns:
RPC + REST + Permission + DTO + Domain/Application declaration

Developer-owned PO owns:
Persistence schema

Domain compiler owns:
PO -> Entity
Entity -> basic Repository CRUD interface
Repository CRUD implementation
STOP
```

The framework may compile, register, adapt, validate, and enforce these declarations, but it must not infer business behavior. Application use-case implementations, domain invariants, DTO-to-domain mapping, complex queries, state machines, and cross-domain workflows remain handwritten business code.

## Problem statement

The current `yunka domain` pipeline treats PO structs as a broad schema input and generates a complete CRUD stack:

```text
PO
  -> Entity
  -> Application Service and DefaultService CRUD behavior
  -> Repository interface and implementation
  -> REST adapter
  -> domain.proto
  -> protobuf/gRPC output
  -> gRPC bridge
  -> wiring
```

At the same time, the canonical protobuf contract pipeline already owns RPC messages/services, explicit REST bindings, operation metadata, and authorization metadata. This produces overlapping authorities:

```text
PO/domain.json decides transport and application shape
PB decides RPC, REST, DTO and Permission shape
```

The overlap creates four structural risks:

1. PB and PO can independently describe different API and DTO models.
2. Generated `DefaultService` embeds application behavior that should be reviewed as business logic.
3. `domain.json` carries transport and protobuf state that duplicates the canonical contract inventory.
4. The framework cannot reliably identify whether a fact came from PB, PO, generated code, or handwritten application code.

C8.4 removes this ambiguity.

## Authority matrix

| Concern | Canonical source | Generated/runtime consumer |
|---|---|---|
| RPC service and method | PB `service` / `rpc` | standard protobuf/gRPC generation |
| REST method, path and body | `google.api.http` | OpenAPI and Yunka REST adapter |
| Request/response DTO | PB messages | generated Go/TypeScript DTOs |
| Domain identity | typed PB file option | Manifest/Application Graph |
| Application identity | typed PB service option | generated Application Port and graph |
| Use case and Operation ID | typed PB method option | PolicyResolver, diagnostics and graph |
| Permission requirements | typed PB method option | Gateway Authorizer |
| Entity fields | developer-owned PO scan | generated domain entity |
| Table/column/index/type | PO and GORM tags | generated GORM record/repository |
| Basic CRUD repository | PO-derived entity inventory | generated interface and implementation |
| Domain invariants | handwritten domain code | application/domain runtime |
| Application orchestration | handwritten application code | RPC/REST adapters |
| Complex repository query | handwritten repository extension | application query/use case |
| Data-scope predicate | explicit scope policy/repository logic | request scope/data evaluator |

## Non-goals

C8.4 does not:

- encode SQL, table names, GORM tags, or data-scope predicates in PB;
- generate domain invariants, state machines, or cross-domain workflows;
- assume `PB DTO == Domain Entity == PO`;
- introduce a generic DI container, reflection dispatcher, service locator, or hidden registration;
- introduce `grpc-gateway` as a second runtime;
- change the C8.3 Role-to-Permission model;
- change `gateway/authz.Authorizer` decision semantics;
- infer REST routes for RPC methods without explicit PB bindings;
- generate non-trivial repository methods such as joins, aggregates, searches, or specifications.

## PB DSL design

### Typed options

Add a repository-owned typed options contract:

```text
contracts/proto/yunka/dsl/v1/options.proto
```

It extends:

```proto
google.protobuf.FileOptions
google.protobuf.MessageOptions
google.protobuf.ServiceOptions
google.protobuf.MethodOptions
```

Core declarations:

```proto
message DomainDeclaration {
  string name = 1;
  string version = 2;
}

message DTODeclaration {
  DTOKind kind = 1;
}

message ApplicationDeclaration {
  string name = 1;
}

message OperationDeclaration {
  string id = 1;
  string use_case = 2;
  repeated string permissions = 3;
  PermissionMode permission_mode = 4;
  bool tenant_required = 5;
  repeated Authentication authentication = 6;
}
```

The precise field numbers must be frozen when C8.4.1 lands. Renaming or removal after publication is a contract-governed change.

### Example

```proto
syntax = "proto3";

package device.v1;

import "google/api/annotations.proto";
import "yunka/dsl/v1/options.proto";

option go_package = "example.com/biz/contracts/device/v1;devicev1";
option (yunka.dsl.v1.domain) = {
  name: "device"
  version: "v1"
};

message GetMachineRequest {
  string id = 1;
}

message MachineDTO {
  option (yunka.dsl.v1.dto) = {
    kind: DTO_OUTPUT
  };

  string id = 1;
  string serial = 2;
  bool enabled = 3;
}

service DeviceApplication {
  option (yunka.dsl.v1.application) = {
    name: "device_management"
  };

  rpc GetMachine(GetMachineRequest) returns (MachineDTO) {
    option (google.api.http) = {
      get: "/v1/machines/{id}"
    };

    option (yunka.dsl.v1.operation) = {
      id: "device.machine.get"
      use_case: "get_machine"
      permissions: "device.machine.read"
      permission_mode: PERMISSION_ALL
      tenant_required: true
      authentication: AUTHENTICATION_JWT
    };
  }
}
```

### DSL restrictions

PB declarations use stable business identities only. They must not contain:

```text
Go package implementation paths
Go handler or struct names
repository implementation names
SQL or GORM expressions
table or column names
API UUIDs
Button UUIDs
database primary keys
```

### DTO semantics

Every message reachable from an RPC request or response is a DTO by default. A typed message option may classify it as:

```text
DTO_INPUT
DTO_OUTPUT
DTO_SHARED
DTO_EVENT
DTO_VALUE_OBJECT
```

This classification is contract metadata. It does not turn a PB message into a domain entity.

### Compatibility rule

Typed options are canonical. Existing `@yunka.*` directives remain a bounded read-only migration bridge:

1. typed option and directive may coexist during shadow compilation;
2. conflicting values fail the build;
3. generators write typed options only;
4. new comment-only policy declarations are rejected after cutover;
5. final removal of directive parsing is a separately reviewed cleanup.

## Contract Manifest V2

`pkg/contract.Manifest` advances from schema version 1 to schema version 2 and adds explicit declarations for:

```text
Domain
Application
DTO classification
UseCase
Operation
Authorization policy
RPC binding
HTTP binding
```

Recommended normalized relationships:

```text
Domain contains Application
Application contains Operation
Operation accepts DTO
Operation returns DTO
RPC Method exposes Operation
HTTP Route routes_to Operation
Operation requires Permission
```

Manifest normalization must remain deterministic. All IDs and repeated values are sorted and deduplicated. Contract Diff must classify at least the following as breaking:

- Domain or Application identity change;
- Operation ID change or removal;
- request/response DTO incompatibility;
- removal/change of an existing REST binding;
- permission removal/addition that changes effective access semantics;
- authentication or tenant requirement weakening/strengthening without an explicit review classification.

The existing Manifest V1 reader remains available during migration. New generation writes V2 only after C8.4.1 is complete.

## Domain Manifest V3

`domain.json` becomes persistence-only.

Example:

```json
{
  "version": 3,
  "domain": "device",
  "tablePrefix": "biz",
  "tenantScoped": true,
  "objects": [
    {
      "name": "coffee_machine",
      "file": "coffee_machine.go",
      "tableName": "biz_device_coffee_machine",
      "fields": []
    }
  ]
}
```

Remove from the canonical V3 model:

```text
RESTSpec
RPCSpec
REST prefix/base path
RPC service
NoREST / NoRPC generation switches
protobuf field numbers
reserved protobuf field numbers/names
transport generation state
```

Stable protobuf field numbering belongs exclusively to PB source and its compatibility guard, not to the PO manifest.

### Repository contract

Only basic CRUD is generated:

```go
type CoffeeMachineRepository interface {
    Create(context.Context, *domain.CoffeeMachine) error
    Get(context.Context, string) (domain.CoffeeMachine, error)
    List(context.Context, int, int) ([]domain.CoffeeMachine, error)
    Update(context.Context, *domain.CoffeeMachine, uint64) error
    Delete(context.Context, string, uint64) error
}
```

The implementation may continue to own framework-level mechanical concerns:

- trusted tenant extraction from `identity.Principal`;
- request-scope transaction participation;
- optimistic version checking;
- soft delete;
- PO record to entity mapping;
- deterministic table naming;
- explicit migration helper construction.

It must stop before application behavior.

### Explicitly handwritten extensions

The following are never inferred from PO fields:

```text
FindByStatus
Search
Aggregate
Join
Specification
cross-aggregate transaction
state transition
business validation
permission decision
DTO mapping
```

They are implemented as handwritten repository extensions, domain policies, or application use cases.

## PB-driven application output

The contract compiler may generate an Application Port and transport adapters, but not a default business implementation.

Example generated port:

```go
type DeviceApplication interface {
    GetMachine(
        context.Context,
        *devicev1.GetMachineRequest,
    ) (*devicev1.MachineDTO, error)
}
```

Example handwritten implementation:

```go
type Service struct {
    machines ports.CoffeeMachineRepository
}

func (service *Service) GetMachine(
    ctx context.Context,
    request *devicev1.GetMachineRequest,
) (*devicev1.MachineDTO, error) {
    // Explicit business orchestration and DTO mapping.
}
```

Both REST and RPC adapters invoke the same Application Port and use the same Operation policy:

```text
REST ─┐
      ├─ generated adapter -> Gateway Authorizer -> Application Port
RPC ──┘
```

## Authorization boundary

C8.3 remains authoritative:

```text
PB Method / Operation ──requires──> Permission <──granted── Tenant Role
                                      ↑
                                      │ represents
                                  UI Button
```

C8.4 changes only policy declaration and compilation. It does not change:

- Role-to-Permission storage;
- Button-to-Permission UI metadata;
- Authorizer evaluation semantics;
- fail-closed execution-boundary enforcement;
- trusted Principal rules;
- separation between RBAC and data-scope evaluation.

The generated policy registry must be a static, typed `PolicyResolver` input to Gateway. Application code must not duplicate Role/Permission checks.

## Application Graph integration

Extend the graph schema with explicit contract declarations rather than inferred naming:

```text
Domain
  contains Application
Application
  contains Operation
Operation
  accepts DTO
Operation
  returns DTO
RPC Method
  exposes Operation
HTTP Route
  routes_to Operation
Operation
  governed_by Permission Policy
```

All graph evidence sourced from PB is `declared/high-confidence`. Missing PB declarations produce missing edges, never inferred edges.

## Architecture guards

### PB guards

1. Every exposed service declares one Domain and one Application.
2. Every protected method declares one globally unique Operation ID.
3. Every protected Operation declares at least one valid Permission key.
4. Public and protected policy declarations cannot coexist.
5. HTTP method/path pairs are unique.
6. Operation IDs are unique across the canonical inventory.
7. PB must not contain SQL, table, GORM, or implementation path metadata.
8. Typed option and legacy directive values must match during shadow mode.

### Domain compiler guards

1. `app/cmd/domain` must not emit `application/**`.
2. `app/cmd/domain` must not emit `transport/**`.
3. `app/cmd/domain` must not emit `wire/**`.
4. `app/cmd/domain` must not emit `.proto` or `.pb.go` files.
5. `app/cmd/domain` must not invoke `protoc`.
6. Domain Manifest V3 must not contain REST/RPC/Permission/protobuf-number fields.
7. Generated files must retain the canonical generated marker and deterministic formatting.
8. Stale generated cleanup must never delete developer-owned files.

### Dependency guards

```text
domain        -> no PB, gRPC, Gateway or persistence dependency
ports         -> domain only
persistence   -> domain + ports + requestscope + GORM
application   -> PB DTO + domain + ports
transport     -> application port + PB + Gateway adapter seams
Gateway       -> no concrete business persistence package
```


## Generated-file ownership

Framework-owned and never hand-edited:

```text
zz_yunka_*
standard protobuf generated files
contracts/generated/**
normalized generated policy registries
```

Application-owned:

```text
PB source declarations
PO source structs
handwritten domain behavior
handwritten application implementations
DTO-domain mapping
complex repository extensions
state machines
cross-domain workflows
```

Stale cleanup may remove only recognized generated files. A file without the canonical generated marker is developer-owned and must never be deleted automatically.

## Acceptance criteria

C8.4 is complete only when all of the following are true:

1. PB is the only writable source for RPC, REST, DTO, Domain/Application, Operation and Permission declarations.
2. Contract Manifest V2 is deterministic and guarded for compatibility.
3. `yunka domain` produces only Entity and basic Repository CRUD artifacts.
4. `yunka domain` contains no protoc, REST, RPC, Application DefaultService, or Wire generation path.
5. REST and RPC invoke the same generated Application Port and the same Gateway Authorizer policy.
6. Business use-case implementation remains handwritten and compiler-checked.
7. Repository tenant isolation derives only from trusted Principal/request scope.
8. No PB declaration contains SQL or storage implementation details.
9. Application Graph represents Domain/Application/Operation/DTO/Permission relationships from declared PB evidence.
10. Dependency, architecture, contract, authz, test, race, vet, vulnerability, build, determinism, and MySQL integration gates pass.
11. Generated regeneration produces a clean worktree.
12. Legacy full-stack domain generation and obsolete PO setter generation are removed.

## Self-check

### Scope

The wave changes compiler and generator ownership. It does not redesign Gateway authorization, request scope, module lifecycle, or the RPC runtime.

### Dependency

No new reflection/DI/runtime dependency is required. Standard protobuf options and the existing split Google API annotations remain the contract mechanism.

### Quality

Every generated output is deterministic, statically typed, zero-drift checked, and covered by contract compatibility classification.

### Risks

The largest risk is silent behavior loss when removing generated `DefaultService`. Migration fixtures must explicitly prove ID/version/timestamp/transaction/tenant behavior before cutover.

### Rollback

Each additive subwave is independently revertible. The destructive legacy removal is isolated in C8.4.4 and does not include database or Permission data changes.
