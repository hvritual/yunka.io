# C10.2 — Canonical Module Binding + Compiler CLI

## Decision

C10.2 does not add a second writable module-binding DSL and does not extend `.yunka/project.json` with Go package facts.

Canonical compiler-local Go binding is derived from existing generated module source under an explicit `--module-root`:

- `<module>/module.go` owns the explicit `ModuleName` literal;
- `<module>/autoload/register.go` owns the explicit Go import path and must contain `modulecatalog.MustRegister(module.GeneratedDescriptor())`;
- `<module>/zz_yunka_module_gen.go` owns the static generated descriptor facts: Version, DependsOn, Requirements, and the runtime-only Build symbol.

The compiler parses only those fixed files with the Go AST. It does not import or execute module packages, run `init`, use `go/packages`, scan arbitrary packages, or infer identity/import paths from directory/module names.

## Generated module composition

The binding compiler emits `assembly/zz_yunka_modules_gen.go` with an explicit `NewCatalog()`:

1. import every selected module by its discovered explicit Go import path;
2. create `modulecatalog.New()`;
3. call `catalog.Register(<alias>.GeneratedDescriptor())` for every selected module in deterministic order;
4. seal the catalog;
5. return the explicit catalog to the handwritten/runtime boundary.

`modulecatalog.Default()` and blank-import activation are not required by generated C10.2 assembly.

## Compiler CLI

C10.2 adds a dedicated top-level command:

```text
yunka assembly generate
yunka assembly check
yunka assembly inspect
```

Inputs remain owned by their existing canonical sources:

- protobuf Contract: `--proto-dir` / `--sources`;
- generated static modules: `--module-root`;
- generated assembly artifact directory: `--out`;
- generated typed Go root/import: `--code-out` / `--code-import`.

`yunka assembly generate` owns only:

- `contracts/generated/assembly-plan.json`;
- `assembly/zz_yunka_assembly_gen.go`;
- `assembly/zz_yunka_modules_gen.go`.

It does **not** regenerate C9 Application ports, policies, REST adapters, or gRPC adapters. Those remain owned by `yunka contract generate`.

## Fail-closed rules

- AssemblyPlan module set and discovered Go binding set must match exactly.
- Module identity is read from `ModuleName`, never from the directory name.
- Autoload evidence must be the exact generated registration call.
- Descriptor parsing accepts only current static fields: Name, Version, DependsOn, Requirements, Build.
- Build is validated as a runtime-only function identifier but is not serialized into AssemblyPlan.
- Unknown descriptor or requirement fields fail closed so a future module schema cannot silently lose assembly facts.
- Missing generated bindings fail before Go generation.
- `check` compares canonical AssemblyPlan bytes and both managed Go outputs; drift is blocking.

## Developer sequence

The current C10.2 workflow is intentionally explicit:

```text
yunka contract generate ...
        ↓
C9 typed Application / REST / gRPC artifacts
        ↓
yunka assembly generate --module-root ... --code-out ... --code-import ...
        ↓
AssemblyPlan + typed Application composition + explicit module catalog
        ↓
yunka assembly check ...
```

C10.3 will consume these generated seams through the existing `kernel.New`, Platform Provider, Executor, Health, Diagnostics, Graph, and dev-runtime owners. C10.2 does not start processes or create a second runtime.

## Verification status

Repository tests cover module-binding discovery, static descriptor projection, exact binding selection, explicit catalog generation, source-order determinism, generated artifact zero drift, typed factory compile boundary, and C10.2 architecture constraints.

Native Yunka GitHub Actions remains an infrastructure blocker while jobs terminate before checkout with no steps. Until an executable exact-head runner is available, these tests are present but full repository qualification remains open.
