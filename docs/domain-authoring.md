# PB DSL and domain persistence authoring

C8.4 separates API/application declarations from persistence declarations. There are two writable sources of truth and they do not overlap:

```text
Protobuf owns:
RPC + REST + DTO + Domain/Application + Operation + Permission declarations

Developer-owned PO owns:
persistence schema
```

`yunka domain` is deliberately small. It scans PO structs and generates only Entity and basic Repository persistence code, then stops. It never generates Application behavior, REST/RPC adapters, protobuf source, protobuf Go files, gRPC registration, or wiring.

## 1. Declare the application contract in PB

Import the typed Yunka DSL:

```proto
syntax = "proto3";

package device.v1;

import "google/api/annotations.proto";
import "yunka/dsl/v1/options.proto";

option go_package = "example.com/biz/contracts/device/v1;devicev1";
option (yunka.dsl.v1.domain) = {
  name: "device"
  version: "v1"
};

message GetMachineRequest {
  string id = 1;
}

message MachineDTO {
  option (yunka.dsl.v1.dto) = { kind: DTO_OUTPUT };

  string id = 1;
  string serial = 2;
}

service DeviceApplication {
  option (yunka.dsl.v1.application) = {
    name: "device_management"
  };

  rpc GetMachine(GetMachineRequest) returns (MachineDTO) {
    option (google.api.http) = {
      get: "/v1/machines/{id}"
    };

    option (yunka.dsl.v1.operation) = {
      id: "device.machine.get"
      use_case: "get_machine"
      permissions: "device.machine.read"
      permission_mode: PERMISSION_ALL
      tenant_required: true
      authentication: AUTHENTICATION_JWT
    };
  }
}
```

The stable business identities are `domain`, `application`, `operation`, `use_case`, and `permission`. Do not derive them from HTTP paths, API UUIDs, button UUIDs, database IDs, Go handler names, or table names.

Messages reachable as request/response DTOs from a typed Application are classified automatically as input/output/shared when no explicit `dto` option is present. An explicit DTO classification remains authoritative.

PB must not contain SQL, GORM tags, table names, repository implementation names, or data-scope predicates.

## 2. Generate and check the PB contract

The contract compiler produces the normalized manifest, OpenAPI, TypeScript client, Application Port, static policy registry, and transport adapters. For a project with typed Applications, both application output arguments are mandatory:

```bash
yunka contract generate \
  --proto-dir ./contracts/proto \
  --out ./contracts/generated \
  --application-out ./internal \
  --application-import example.com/biz/internal
```

Check zero drift with the same output mapping:

```bash
yunka contract check \
  --proto-dir ./contracts/proto \
  --out ./contracts/generated \
  --application-out ./internal \
  --application-import example.com/biz/internal
```

The standard protobuf Go/gRPC plugins remain the PB Go-code generator. C8.4 does not reintroduce a custom protobuf runtime or generator. `go_package` is therefore the source used by generated Application/transport adapters to reference the standard generated protobuf types.

Generated PB application files are limited to:

```text
internal/<domain>/application/zz_yunka_*_application_port_gen.go
internal/<domain>/policy/zz_yunka_*_operation_policy_gen.go
internal/<domain>/transport/rpc/zz_yunka_*_rpc_adapter_gen.go
internal/<domain>/transport/rest/zz_yunka_*_rest_adapter_gen.go
```

Only files carrying the canonical `// Code generated by yunka contract; DO NOT EDIT.` marker are managed or removed as stale. Handwritten files are never deleted by the contract generator.

The generated Application Port has no implementation:

```go
type DeviceApplication interface {
    GetMachine(
        context.Context,
        *devicev1.GetMachineRequest,
    ) (*devicev1.MachineDTO, error)
}
```

RPC and REST both delegate to this same interface. The policy registry is a static `gateway/authz.PolicyResolver`; authorization remains enforced by the existing Gateway Authorizer rather than by business Application code.

Streaming operations, complex HTTP path templates, nontrivial body-field mapping, or `response_body` mappings that cannot be generated without business semantics fail with an explicit “handwritten adapter” error instead of being guessed.

## 3. Declare persistence with PO

Initialize the project database prefix once:

```bash
yunka init --db-prefix biz
```

Every generated table follows:

```text
<project-prefix>_<domain>_<po-object>
```

Examples:

```text
biz_device_coffee_machine
biz_device_device_group
biz_tenant_member
```

One PO object lives in one snake_case file:

```text
internal/device/infrastructure/persistence/
├── coffee_machine.go   -> type CoffeeMachinePO struct
├── device_group.go     -> type DeviceGroupPO struct
└── site_binding.go     -> type SiteBindingPO struct
```

Example:

```go
package persistence

import "time"

type CoffeeMachinePO struct {
    Serial      string    `gorm:"column:serial;type:varchar(64);index"`
    Enabled     bool      `gorm:"column:enabled;type:tinyint(1)"`
    ActivatedAt time.Time `gorm:"column:activated_at;type:datetime(3)"`

    // Stored by GORM but intentionally excluded from generated Entity fields.
    InternalHash string `gorm:"column:internal_hash;type:varchar(64)" yunka:"-"`
}
```

Fields that map mechanically into generated Entity values support `string`, `int64`, `uint64`, `bool`, `float64`, and `time.Time`. Persistence-only/relational fields may use `yunka:"-"` and remain owned by the PO.

Framework-owned fields must not be redeclared in the developer PO:

```text
id
tenant_id
version
created_at
updated_at
deleted_at
```

## 4. Run the persistence-only domain compiler

Create/adopt a domain:

```bash
yunka domain new --name device
```

After editing PO files:

```bash
yunka domain generate --path internal/device
yunka domain check --root internal
```

The output boundary is fixed:

```text
internal/device/
├── domain.json
├── domain/
│   ├── zz_yunka_coffee_machine_entity_gen.go
│   └── zz_yunka_device_group_entity_gen.go
├── ports/
│   └── zz_yunka_repositories_gen.go
└── infrastructure/persistence/
    ├── coffee_machine.go                       # developer-owned PO
    ├── device_group.go                         # developer-owned PO
    ├── zz_yunka_coffee_machine_record_gen.go
    ├── zz_yunka_device_group_record_gen.go
    └── zz_yunka_repositories_gen.go
```

`domain.json` is Domain Manifest V3. It records only persistence/domain inventory such as table prefix, tenant scope, PO object/file/table identity, and mapped persistence fields. It contains no REST/RPC settings and no protobuf field numbers or reserved protobuf slots.

Old V1/V2 manifests are accepted only as deterministic migration input. New writes are V3.

## 5. Repository boundary

For each PO, Yunka generates only basic CRUD:

```go
type CoffeeMachineRepository interface {
    Create(context.Context, *domain.CoffeeMachine) error
    Get(context.Context, string) (domain.CoffeeMachine, error)
    List(context.Context, int, int) ([]domain.CoffeeMachine, error)
    Update(context.Context, *domain.CoffeeMachine, uint64) error
    Delete(context.Context, string, uint64) error
}
```

The generated implementation may own mechanical framework concerns:

- trusted tenant extraction from `identity.Principal`;
- request-scope transaction participation;
- optimistic version checks;
- soft delete;
- PO record ↔ Entity mapping;
- deterministic table naming;
- explicit `AutoMigrate` helper construction.

The compiler stops there.

`AutoMigrate` is an explicit helper. C8.4 no longer generates `wire.Build` or silently performs schema migration as an Application startup side effect. The application/deployment composition decides when migrations are allowed to run.

## 6. Handwrite business Application behavior

DTO, Entity, and PO are deliberately separate models:

```text
PB DTO != Domain Entity != Persistence PO
```

Matching field names are not permission to infer business mappings.

A handwritten implementation owns use-case orchestration:

```go
type Service struct {
    machines ports.CoffeeMachineRepository
}

func (service *Service) GetMachine(
    ctx context.Context,
    request *devicev1.GetMachineRequest,
) (*devicev1.MachineDTO, error) {
    // Explicit repository use, business rules and DTO mapping.
}
```

Also handwritten:

```text
business invariants
DTO ↔ Domain mapping
FindByStatus/Search/Aggregate queries
joins/specifications
state transitions
state machines
cross-aggregate transactions
cross-domain workflows
data-scope evaluation
```

Application code does not duplicate Role/Permission checks. PB declares the Operation policy; Gateway Authorizer decides it at the execution boundary.

## 7. Authorization model

C8.3 remains unchanged:

```text
PB Method / Operation ──requires──> Permission <──granted── Tenant Role
                                      ^
                                      │ represents
                                  UI Button
```

REST and RPC generated from the same PB use the same Operation ID, Permission set and Application Port. UI Button mappings remain UI metadata, not authorization grants.

Resource/data-scope predicates are not encoded in PB.

## 8. Compatibility and cutover rules

Typed protobuf options are the canonical writable form. The parser may still read historical `@yunka.*` authorization comments as a migration bridge, but canonical repository PB sources are not allowed to add comment-only policy declarations.

During shadow migration, typed and legacy declarations may coexist only when they normalize to the same policy. A conflict fails compilation.

Contract compatibility classifies Domain/Application/Operation/UseCase/DTO identity and authorization semantic changes in addition to normal protobuf and HTTP compatibility.

## 9. Verification

Repository-level C8.4 gates are:

```bash
make domain-check
make dsl-check
make contract-check
make architecture-check
make authz-check
make verify
```

Production verification additionally requires the repository integration gate:

```bash
YUNKA_TEST_MYSQL_DSN="..." make verify-production
```

`make domain-check` locks the PO → Entity → Repository CRUD → STOP boundary. `make dsl-check` validates typed contract parsing, Application Graph declarations, code generation and architecture policy. The full `make verify` includes both gates.

## Ownership summary

Framework-generated and never hand-edited:

```text
contracts/generated/**
standard protobuf generated Go files
internal/<domain>/domain/zz_yunka_*
internal/<domain>/ports/zz_yunka_*
internal/<domain>/infrastructure/persistence/zz_yunka_*
internal/<domain>/application/zz_yunka_*
internal/<domain>/policy/zz_yunka_*
internal/<domain>/transport/**/zz_yunka_*
```

Developer-owned:

```text
PB source declarations
PO source structs
handwritten Domain behavior
handwritten Application implementations
DTO ↔ Domain mapping
complex Repository extensions
state machines
cross-domain workflows
migration execution policy
```
